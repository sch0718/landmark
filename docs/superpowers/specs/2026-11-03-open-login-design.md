# 로그인 공개(누구나 동기화) 설계 메모

보관함 동기화 로그인은 Pages 변수 `ALLOWED_EMAILS`·`ALLOWED_ACCOUNTS`로 운영자 본인에게만 열려 있다. 이 변수가 **둘 다 없으면 누구나**, **하나라도 있으면 지금처럼 목록 안만** 쓰게 바꾼다. 공개 뒤 한 사람이 무료 D1을 독차지하지 못하게 사용자별 저장 상한을 둔다.

- 작성일: 2026-11-03
- 전제: 무료 운영(D1 하나 500MB, 읽기 500만 행/일·쓰기 10만 행/일·Functions 10만 요청/일을 가즈아와 함께 씀), 사용자는 운영자 본인과 소수. 공급자마다 보관함이 따로인 지금 동작은 유지한다(계정 연결·병합 없음).
- 기존 장치로 안 되는 이유: 허용 목록 검사는 목록이 비면 모두 거절하고, 보관함 항목에는 하루 쓰기 한도(`sync-items` 30,000)만 있고 총량 상한이 없다.

## 열림·제한 판정

| `ALLOWED_EMAILS` | `ALLOWED_ACCOUNTS` | 동작 |
|---|---|---|
| 없음 | 없음 | 열림: Google·카카오·네이버 누구나 |
| 있음(빈 값 포함) | 없음 | 지금과 같음: 목록의 Google 이메일만, 카카오·네이버 모두 거절 |
| 없음 | 있음 | 지금과 같음: 목록의 카카오·네이버 계정만, Google 모두 거절 |
| 있음 | 있음 | 지금과 같음 |

- 「없음」은 변수가 정의되지 않은 경우(`undefined`)만이다. 빈 문자열은 「있음」이라 모두 거절한다(지금 동작 그대로).
- 판정은 `src/server/library-sync/auth.ts`의 함수 하나에 두고, 로그인(`sessionAuthFor`)과 AI 연결 토큰 검사(`src/server/agent/auth.ts`)가 같이 쓴다.
- 개발용 가짜 로그인의 `kakao:dev-me,naver:dev-me` 기본값은 지운다. 변수가 없으면 열림이라 기본값이 필요 없다. 거절 화면을 보려면 지금 문서의 명령처럼 `ALLOWED_ACCOUNTS`를 넘긴다.
- 공용 패키지 `@sch0718/firebase-session`은 목록이 비면 모두 거절한다. gazua 초대 가입 작업이 더하는 `isAllowed` 콜백(sch0718/sch0718-toolkit-web#24, 「목록에 없으면 서비스에 묻는다」, 기존 호출의 의미는 그대로)을 쓴다. 열림이면 `isAllowed: () => true`를 넘긴다. 순서: 패키지 PR 병합·발행 → landmark가 그 버전으로 올림 → landmark PR. 이 작업에서 패키지를 따로 고치지 않는다.

## 사용자별 상한

운영 실측(2026-11-03, 읽기 전용 조회): 운영자 계정당 3,420항목, 문서 합계 1,947,972바이트(가장 큰 항목 3,871자), D1 전체 8.9MB(같은 보관함 3계정 + 색인·백업 등).

| 대상 | 상한 | 근거 |
|---|---|---|
| 보관함 항목 수(묘비 포함) | **5,000개** | 운영자의 약 1.5배. 사용자 선택(2026-11-03) |
| 보관함 문서 바이트(`doc` UTF-8 합) | **5MB**(5,000,000) | 운영자의 약 2.6배. 꽉 채운 계정은 색인 포함 약 8MB라 약 60계정이 모여야 500MB |
| 하루 항목 쓰기(`sync-items`) | 30,000 → **5,000** | 사용자 선택. 한 사람이 가즈아와 함께 쓰는 하루 쓰기 10만 행을 크게 쓰지 못하게. 보낸 항목 수로 세므로(바뀌지 않은 것·거절된 것·다시 보낸 것 포함) 상한 가까운 보관함의 첫 올리기는 중간에 429가 날 수 있고, 남은 것은 다음 날(UTC) 자동 동기화 때 이어서 올라간다 |
| 하루 올리기·받기 요청 | push 2,000 → **500**, pull 5,000 → **2,000** | 운영자 실측 하루 최대 push 35·pull 9회. 상한 검사가 push마다 사용자 행(최대 5,000)을 세므로 읽기를 막는다. 한 사람 최대 약 500×5,000 + 2,000×501 ≈ 350만 행/일. 사용자 선택(2026-11-03, 개수·바이트를 표에 저장하는 스키마 변경 대신) |
| 기기 행(`library_devices`) | **20개** | 기기 ID를 바꿔 가며 받기를 부르면 행이 계속 늘어난다. 표시용이라 넘으면 새 기기만 목록에 안 남는다. 지워지는 것은 연결 해제·철회·계정 삭제 때뿐이라, 로그아웃 없이 오래 쓰면 새 기기가 목록에 안 보일 수 있다(동기화는 됨). 한계로 둔다 |

- 상한 검사는 push에서 늘어나는 항목에만 한다. 새 항목이나 문서가 커지는 수정이 상한을 넘기면 그 항목만 `too-large`로 거절하고, 서버에 있던 항목의 삭제(묘비)와 줄어드는 수정은 늘 받는다. 묘비는 `deletedAt` 시각만큼 커지므로 살아 있던 항목을 지울 때만 64바이트(`TOMBSTONE_GROWTH_BYTES`)까지 면제하고(이미 묘비인 항목의 수정은 면제하지 않는다), 그보다 커지는 묘비는 다른 수정처럼 상한을 적용한다(큰 묘비로 바이트 상한을 피하지 못하게). 서버에 없던 항목의 묘비는 새 항목으로 센다(묘비를 무한히 쌓지 못하게). 상한에 닿은 뒤에만 생기는 드문 경우라, 그 묘비가 「올리지 못한 항목」에 남는 것은 감수한다. 거절 사유를 새로 만들지 않아 옛 클라이언트의 저장 형식 검사(`storage.ts`)가 깨지지 않는다.
- 늘어나는 항목이 있을 때만 사용자 행 전체의 개수·바이트를 한 번 센다(계정당 수천 행 읽기). 같은 묶음의 줄어드는 수정·삭제 절약분은 먼저 빼고 센다. 세는 것과 쓰는 것 사이에 다른 push가 끼면 함께 통과해 넘칠 수 있다. 동시에 보낸 push 수 × 최대 1MB까지이고, 하루 항목 한도(5,000개 ≈ push 50개)로 묶여 최악에도 약 50MB다. 드물고 다음 push부터 다시 막히므로 감수한다.
- 삭제한 항목은 묘비로 90일 남았다가 정리되므로 그 뒤에 자리가 난다. 클라이언트는 거절된 항목을 내용이 바뀔 때까지 다시 보내지 않으므로(`dirtyItems`), 자리가 난 뒤 그 항목을 고쳐야 다시 올라간다. 문구에 적는다.
- 앱 문구: `too-large` 거절 문구에 상한(항목 하나 20만 자, 보관함 5,000개·5MB)과 「자리가 난 뒤 이 항목을 고치면 다시 올라가요」를 붙인다.

### 이미 막혀 있어 그대로 두는 곳

| 경로 | 지금 장치 |
|---|---|
| 서버 백업 | 사용자당 1개, 1MB, 하루 쓰기 20회 |
| 받은함 | 대기 20개, 30일 만료, 하루 50회 |
| AI 연결 토큰 | 활성 10개, 하루 만들기 20회 |
| 짧은 링크·여행 공유·약속 | 로그인과 무관하게 이미 누구나 쓰는 기능. IP·일 한도와 만료가 있다 |
| 로그인(세션·사용자 행) | IP당 하루 60회(`sync-login`). 계정마다 실제 Google·카카오·네이버 계정이 필요해 대량 가입 비용이 크다. 더 보태지 않는다 |

## 앱 문구

- 허용 목록 때문에 막힌 경우의 「이 계정은 아직 동기화를 쓸 수 없어요 … 관리자에게 이 값을 알려 주세요」는 제한 모드에서만 나오므로 그대로 맞다.

## 공개 절차(사용자)

1. 배포 전에 Preview·Production 모두 두 변수 중 하나 이상이 있는지 확인한다(둘 다 없는 환경은 배포 순간 열린다). 배포하고 운영에서 동기화가 그대로 되는지 확인한다.
2. Cloudflare Pages 운영 변수에서 `ALLOWED_EMAILS`와 `ALLOWED_ACCOUNTS`를 **둘 다** 지우고 다시 배포한다. 하나만 지우면 그 공급자는 계속 모두 거절된다.
3. 되돌리려면 두 변수를 다시 넣고 재배포한다.
