# 많은 장소·라벨 다루기 (개선 묶음 D)

## 목표와 범위

장소 3,202곳·라벨 53개에서도 찾기와 거르기가 쉽고 장소 선택에 즉시 반응하게 한다. 보관함 v2와 선호 스키마는 바꾸지 않는다. 아이콘·공유 화면 소스, 사용자 백업은 수정하거나 복사하지 않는다. 의존성·네트워크·git 작업은 추가하지 않는다.

## 화면 동작

- 라벨 12개까지는 기존 칩, 13개부터 관리 링크 다음에 `라벨 찾기` 버튼을 둔다. 창은 열 때 lazy로 받는다. 넓은·중간 화면은 대화상자, 휴대폰은 아래 시트다.
- 이름 부분 일치 검색(NFC 한글), 아이콘·색·이름·현재 조건의 장소 수를 표시한 체크 목록을 제공한다. 체크 즉시 기존 query.labelIds에 반영하고 미분류를 해제한다. 하나라도/모두 포함도 기존 query.mode를 함께 쓴다. 완료·Esc·바깥 누르기로 닫고 버튼으로 포커스를 돌린다.
- 창 정렬은 내 순서(order, 기본)/많은 순(동수는 내 순서)이며 창을 닫으면 초기화한다. 저장하지 않는다. 칩은 고른 라벨을 먼저, 각 묶음 안에서는 내 순서를 지킨다.
- 가로 칩 줄은 넓은·중간에서 넘칠 때만 양끝에 44px 스크롤 버튼을 둔다. 끝 방향 버튼은 비활성화한다. 휴대폰은 기존 터치 스크롤을 쓴다. 크기·내용·스크롤 변경을 관찰한다.
- 지역 첫 줄은 시·도별 장소 수 내림차순(동수 이름순, 기타 마지막)이다. 도를 누르면 도 전체로 거르고 시·군 줄을 펼친다. 시·군을 고르면 해당 도 전체 대신 그 시·군으로 거른다. 다른 시·도와는 OR다. 특별·광역시·세종은 한 단계다. 선택 항목은 0곳이 되어도 해제할 수 있게 남긴다.

도 지역의 두 번째 토큰에서 시·군을 뗀다. 도만 확인되면 도 전체에 속한다. 시·도를 못 정하면 10km 안 주소가 확인된 가장 가까운 장소에서 빌리거나 기타다. 같은 거리이면 입력에서 뒤의 장소를 택하며 빌린 지역은 다시 빌려주지 않는다. 기존 단일 지역 계산은 그대로 유지해 목록 묶음·옛 거르기의 의미를 보존한다.

## 저장값 호환

query.regions 문자열 배열 그대로 사용한다. 새 값은 `강원/전체`(도 전체), `강원/강릉`(시·군), `서울/전체`(광역시), `기타/전체`다. 옛 `강릉` 등은 기존 단일 지역 기준으로 계속 거른다. 새 화면은 옛 선택값도 보여 주고 해제할 수 있다. 옛 앱은 새 `강원/전체`·`강원/강릉`을 알지 못하므로 결과가 0일 수 있다. 기존 빈 결과의 `필터 지우기`로 복구 가능하다. `서울`·`제주`·`광주` 같은 옛 단일 값은 기존 의미로 동작한다. 특히 옛 `제주`는 제주시, 옛 `광주`는 광역시와 경기도 광주시를 함께 뜻하므로 새 시·도 전체는 반드시 `/전체`로 구별한다. 스키마 버전이나 라벨·장소 저장 데이터는 바꾸지 않는다.

## 성능 설계와 측정

장소 레코드 정체성별 livePlaces 배열과 배열별 지역 결과를 WeakMap으로 공유한다. 장소 레코드 객체가 바뀌면 새 계산을 한다. 같은 보관함 문서의 목록·질의·칩 세기는 한 배열과 결과를 쓴다. 저장소가 문서 전체를 재해석해 객체를 새로 만들면(라벨·여행 저장 포함) 다시 계산한다. 가까운 장소 후보는 0.1도 격자로 좁힌 뒤 기존 haversine과 동률 규칙으로 비교한다. 경도 ±180도·극지방도 후보를 빠뜨리지 않는다.

보관함 지도는 기본 마커와 선택 마커를 분리한다. 장소 선택은 기본 마커 배열·supercluster 색인을 유지하고 선택 마커만 별도 전달한다. 선택된 장소는 색인 위에 개별 표시한다(묶음 수에는 계속 포함된다). 네이버 오버레이 전체 재생성은 우선 유지하고 색인 재구성을 막는다.

측정 스크립트: `node_modules/.bin/tsx --tsconfig tsconfig.app.json scripts/bench-library.mts <백업 경로>`. 백업은 메모리에서만 읽고 출력은 개수·시간뿐이다. 이전 중첩 비교와 개선 계산(처음/공유 재호출), query·칩 세기 묶음, 색인 재구성/선택 전달을 반복해 중앙값을 기록한다. 측정은 Node 24.1.0, 준비 3회 뒤 15회 중앙값이다. 값은 기기·부하에 따라 달라진다.

| 항목 | 개선 전(ms) | 개선 후(ms) |
| --- | ---: | ---: |
| 기존 단일 지역 계산(같은 입력, 처음) | 34.425167 | 15.717625 |
| 새 계층 지역 계산(처음, 단일 지역 계산과 별도) | 없음 | 2.212792 |
| 같은 입력의 지역 재호출 | 약 35.247 | 0.000166 |
| 질의 + 라벨 수 + 지역 수 묶음(같은 보관함) | 113.197 | 1.789625 |
| 장소 선택 시 마커 준비 + 색인 구성 | 2.680459 | 0.000292 |

개선 전 질의 묶음·공유 재호출은 수정 전에 실제 실행한 중앙값이고, 단일 지역 계산과 마커 준비는 스크립트가 이전 구현을 함께 실행해 비교한다. 개선 후 지역 수는 새 두 단계 세기를 쓴다. 선택 측정은 마커 데이터 준비·색인 구성의 CPU 시간이며 SDK 오버레이 그리기·브라우저 렌더 시간은 포함하지 않는다. 선택만 바꾸면 색인 구성 횟수는 0이다.

이 환경은 tsx CLI가 IPC 소켓을 열 때 EPERM으로 실패하므로 같은 로더를 직접 쓰는 아래 명령으로 측정했다.

```sh
export PATH="/opt/homebrew/opt/node@24/bin:$PATH"
TSX_TSCONFIG_PATH=tsconfig.app.json node --import tsx scripts/bench-library.mts <백업 경로>
```

## 구현·시험 순서

1. 기존 계산을 담은 측정 스크립트로 기준을 기록한다.
2. 단위 시험을 먼저 추가하고 실패를 확인한 뒤 지역 표·격자·캐시·두 단계 세기/거르기를 구현한다.
3. 라벨 찾기·선택 우선·넘침 스크롤 단위 시험 뒤 UI와 lazy 등록을 구현한다.
4. 기본 마커 정체성과 선택 변경·색인 유지 시험 뒤 지도 선택 경로를 분리한다.
5. desktop·iphone·galaxy에서 라벨 검색 선택→마커 감소, 시·도→시·군 거르기를 E2E로 확인한다.
6. lint, build:ci(단위·타입·번들 예산), 기존 library E2E와 새 E2E를 실행하고 측정값을 기록한다. E2E는 `E2E_PORT=5178`로 돌린다(공유 지도 서버는 기본 5174).

## 시험 범위

17개 시·도 별칭 전체, 두 단계 개수와 OR 거르기, 옛 값·빈 결과 복구, 동일 입력 지역 캐시와 불변 갱신, 기존 계산과 무작위·격자 경계·10km·동률·날짜변경선·극지방 비교를 포함한다. 라벨 검색·정렬·여러 선택·모드·필터 반영·선택 우선·12/13 경계·넘침 조건·키보드·모바일 시트를 시험한다. 초기 JS gzip 예산은 327,680바이트다.


## 확인 결과와 남은 제한

- 전체 단위: 201개 파일, 3,475개 시험 통과, 실패 0. 이후 스크롤 폭 회귀와 위도 격자 경계 시험을 추가·확인했다(최종 지역·라벨·라우트 3개 파일 36개 시험과 실제 목록·마커 연동 추가 1개 시험도 통과, 실패 0).
- `yarn lint`, 타입 검사, 데이터 검증, 앱·지도 빌드 및 모든 lazy 분리 검사 통과. 초기 JS gzip은 최종 빌드에서 319,719바이트로 예산 327,680바이트 이내다.
- `yarn build:ci` 원문은 첫 `yarn validate`의 tsx IPC 소켓 생성이 EPERM으로 실패했다. `TSX_TSCONFIG_PATH=tsconfig.app.json node --import tsx pipeline/cli/validate.ts`로 같은 검증 코드를 실행한 뒤 나머지 CI 단계는 각각 실행했다.
- `E2E_PORT=5178 yarn test:e2e tests/e2e/library.spec.ts`와 `E2E_PORT=5178 yarn test:e2e tests/e2e/large-library.spec.ts`는 둘 다 빌드 후 개발 서버의 `listen ::1:5178`이 EPERM으로 거절되어 브라우저 시험을 시작하지 못했다. E2E 시험 실패가 아니라 환경에 의한 실행 차단이다. desktop·iphone·galaxy의 새 시험은 모두 등록했지만 실제 브라우저 실행은 포트를 열 수 있는 환경에서 확인해야 한다.
- 네이버 오버레이 전체 재생성은 유지한다. 동일 보관함 문서 안에서 캐시는 공유하지만 저장소의 전체 문서 재해석 이후에는 새 계산을 한다.
- 지정된 아이콘·공유 소스는 변경하지 않았다. 백업 내용은 파일로 복사하지 않았고 git 커밋·푸시·브랜치 작업도 하지 않았다.
