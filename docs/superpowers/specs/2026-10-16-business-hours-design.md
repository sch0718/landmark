# 랜드마크 설계 — 영업시간·휴무 경고 (묶음 F6)

- 작성일: 2026-10-16
- 상태: 설계 (리뷰 전)
- 태그: `v0.13.0`, 파일 이름 조각 `business-hours`
- 관련 문서: `2026-10-12-trip-planning-design.md`(시간표·지도 카드·경로 캐시), `2026-10-12-place-adding-design.md`(서버 함수·허용 호스트), `2026-10-14-design-qa-design.md`(접근성 기준). 충돌하면 이 문서가 우선한다.
- 출발점: F1~F5가 모두 병합된 `main`. F6은 F1~F5의 코드에 기대지 않는다. 예외는 F5의 하루 경계 상수 `DAY_ROLLOVER_HOUR` 하나(§3.2, §10).

## 1. 배경과 목표

### 1.1 목표

여행 시간표에서 **도착 시각이 그 장소의 영업시간 밖이거나 휴무일이면** 그 행에 경고를 보인다.

- 예: `15:40 도착 — 브레이크타임 15:00~16:30`, `휴무일 — 정기휴무 (매주 수요일)`.
- 구글·네이버는 영업시간을 보여 주지만 **내 일정의 도착 시각과 맞춰 보지 않는다**. 이것이 차별점이다.
- 영업 정보에는 늘 **확인한 날짜**를 함께 보인다. 정보가 없으면 `영업시간 확인 필요`로 남기고 추측해서 채우지 않는다(작업 공간 CLAUDE.md 원칙).

성공 기준:

1. 네이버 장소를 Day에 넣으면, 따로 누르지 않아도 몇 초 안에 그 행에 경고(또는 아무것도 없음)가 나온다.
2. 순서·출발 시각·체류 시간·고정 시각을 바꾸면 경고가 바로 다시 계산된다(새 요청 없이).
3. 지도 카드에서 그날 영업시간·확인 날짜를 보고 `다시 확인`으로 새로 받을 수 있다.
4. 카카오·구글·핀 장소, 네이버에 정보가 없는 장소, 받지 못한 경우는 모두 `영업시간 확인 필요`.
5. 보관함 저장 형식이 바뀌지 않는다. `v0.12.0`으로 되돌려도 데이터 걱정이 없다.

### 1.2 범위

넣는 것:

- 서버 함수 `GET /api/hours?sid=<네이버 장소 ID>[&fresh=1]`(§4.1).
- 기기 캐시 `tripmap:hours:v1`(§4.2)와 다시 받기 규칙(§4.3).
- 판정(§3): 휴무일·임시 휴무·영업 전·영업 끝·브레이크타임·라스트오더·머무는 중 영업 끝·머무는 중 브레이크타임.
- 화면(§2): 시간표의 장소 행 한 줄, 지도 카드의 `영업시간` 칸.

안 하는 것:

- 카카오·구글·핀 장소의 영업시간(받을 길이 없다 — §12-6).
- 공휴일 계산(§3.5, §12-4). 공휴일 규칙은 카드에 글로만 보인다.
- 여행 당일 모드(F5) 화면의 경고(§12-5). 쓸 수 있게 조각만 내보낸다.
- 지도 핀 색·모양 변경, Day 탭 배지, 보관함 화면의 영업시간 표시.
- 예약 필요 여부, 메뉴·가격.
- 경고를 피하도록 순서를 자동으로 바꾸기(`순서 정리`는 그대로).

### 1.3 지금 있는 것

- 시간표: `computeSchedule`(`src/domain/trips/schedule.ts`)가 점마다 `arriveMin`·`departMin`(Day 0시 기준 절대 분, 자정을 넘기면 1440 이상)을 준다. 계획 화면이 `useDayPlan`으로 고른 Day만 한 번 구해 지도·시간표가 함께 쓴다.
- 장소 행: `StopRow`(`DayTimeline.tsx`)에 도착 시각·이름·체류·고정 시각(늦음은 `error.main`).
- 지도 카드: `MapCard.tsx`(이름·분류·위치·체류/고정 입력·버튼). 지금은 `plan`을 받지 않는다.
- 서버: `handleGet`(출처 검사 → 입력 → 엣지 캐시 → 해석 → 저장), `makeRequester`(허용 호스트 정확 일치·`redirect: 'manual'`·8초). `pcmap.place.naver.com`은 이미 `ALLOWED_HOSTS`에 있다.
- 경로 캐시 `tripmap:routes:v1`(`RouteLookup`)이 보관함과 따로 있는 기기 캐시의 본보기다. 보관함 저장이 용량을 넘으면 경로 캐시를 지우고 다시 쓴다(`library-store.ts`의 `putItem`).

### 1.4 조사 결과 (2026-10-16, 요청 10번)

**장소 요약 API**(`map.naver.com/p/api/place/summary/<sid>`)는 쓸 수 없다.

- `data.placeDetail.businessHours`는 `{ "description": "<문장 하나>" }`뿐이다. 문장은 **조회한 순간 기준의 다음 변화**다.
  - 카페 1958911015: `23:30에 라스트오더` / 식당 12028621: `20:00에 라스트오더` / 식당 11815720: `15:00에 브레이크타임`.
  - 학교 11591557: `businessHours: null`.
- 요일별 시간·브레이크타임·휴무가 없어서 내 도착 시각과 맞출 수 없다.

**장소 홈 HTML**(`https://pcmap.place.naver.com/<업종>/<sid>/home`)에 구조가 있다.

- 응답은 HTML 약 370~400KB. 안의 `window.__APOLLO_STATE__ = {…}` 에 `"newBusinessHours":[…]`가 **딱 한 번** 나온다(4곳 모두). 상태 객체 뒤에 다른 스크립트가 붙어 있어 `</script>`까지 잘라 JSON으로 읽을 수는 없다 — 그 배열만 괄호를 맞춰 떼어 읽는다.
- `/place/<sid>/home`으로 부르면 식당·카페는 `302` → `/restaurant/<sid>/home`, 박물관(11612628)은 이동 없이 200. 이동을 따라가면 된다.
- 배열 항목(`NewBusinessHour`) 모양 — 확인한 4곳(카페·생선구이·냉면·박물관):

```jsonc
{
  "name": "" | "기본",
  "businessStatusDescription": { "status": "영업 중", "description": "14:30에 브레이크타임" }, // 조회 순간 기준, 안 씀
  "businessHours": [               // 요일별. 조회한 날의 요일부터 시작한다(금요일에 받으면 금,토,…,목)
    { "day": "금",                 // '월'~'일', 또는 '매일'(항목 하나만)
      "businessHours": { "start": "11:00", "end": "21:00" },   // 휴무 요일은 null. 끝이 "24:00"인 곳 있음
      "breakHours": [{ "start": "14:30", "end": "16:30" }],    // null 또는 [] 도 옴
      "lastOrderTimes": [{ "type": "영업시간", "time": "19:40" }], // null 도 옴
      "description": null,         // 휴무 요일: "정기휴무 (매주 수요일)"
      "showEndsNextDay": false }   // 휴무 요일은 null
  ],
  "comingIrregularClosedDays": [], // 네 곳 모두 빈 배열
  "comingRegularClosedDays": "",   // 네 곳 모두 빈 문자열
  "freeText": "라스트오더 점심14:30 /저녁19:30"   // 자유 글. 빈 문자열이 많다
}
```

- 업종 차이: 카페·식당·박물관 모두 같은 모양. 식당만 `breakHours`·`lastOrderTimes`가 찼다. `isBizHourMissing`·`hideBusinessHours` 표시는 실제 값과 어긋나(값이 있는데 `true`) 쓰지 않는다.
- **확인하지 못한 것**(받은 값이 없어 본 적이 없다): 자정을 넘는 영업(`showEndsNextDay: true`나 끝 < 시작)의 실제 모양, 24시간 영업 표기, `comingIrregularClosedDays`·`comingRegularClosedDays`가 찼을 때의 형식, `공휴일`·`평일`·`주말` 같은 `day` 표기, 이름이 다른 항목이 둘 이상인 예, 없는 sid·영업시간 없는 장소(학교 등)의 홈 응답, 요청 빈도 한도, Cloudflare 서버에서의 접속 가능 여부. 설계는 이것들을 **모르는 값으로 다뤄 `확인 필요`로 떨어지게** 한다(§3·§6).
- 카카오·구글·핀: 이번에 조사하지 않았다. 지금 서버가 받는 카카오 응답(`panel3`)에 영업시간이 있는지는 확인 필요.

## 2. 화면

### 2.1 시간표의 장소 행

`StopRow`의 둘째 줄(체류·고정) 아래에 **한 줄**을 더한다. 경고가 없으면 줄이 없다. 행 버튼(카드 열기) 안에 있어 누르면 카드가 열린다.

| 상태 | 모양 | 문구 예 |
|---|---|---|
| 경고 | 주황 칩(`--tm-label-orange-fill` 바탕, `--tm-label-orange-text` 글자, 굵게) + 앞에 경고 아이콘(`aria-hidden`) | `15:40 도착 — 브레이크타임 15:00~16:30` |
| 확인 필요 | 아이콘 없이 `--tm-text-muted` 12px | `영업시간 확인 필요` |
| 문제없음·받는 중 | 줄 없음 | — |

- 받는 중에는 아무것도 보이지 않는다(받자마자 나타났다 사라지는 깜빡임을 막는다).
- 행마다 경고는 하나만(§3.4의 우선순위로 가장 무거운 것).
- 출발지·숙소 행은 판정하지 않는다.

### 2.2 지도 카드의 `영업시간` 칸

Day의 장소이거나 후보인 장소의 카드에, 체류·고정 입력과 버튼 사이에 칸을 둔다. 출발지·숙소로만 쓰인 장소에는 없다.

```
영업시간                                   (h3, 13px 굵게)
Day 2 · 10.17(토) · 11:00~21:00            (그날 규칙)
브레이크타임 14:30~16:30 · 라스트오더 19:40
[!] 15:40 도착 — 브레이크타임 14:30~16:30   (행과 같은 칩, 있을 때만)
네이버 안내: 라스트오더 점심14:30 /저녁19:30 (freeText가 있을 때)
다가오는 임시 휴무: …                       (있을 때, 원문)
10월 16일 확인 · 네이버   [다시 확인]       (12px 보조 글자, 버튼 44px)
```

- 규칙 줄의 Day: Day의 장소면 **그 장소가 있는 Day**(고른 Day와 달라도), 후보면 **고른 Day**. 후보는 도착 시각이 없어 휴무·임시 휴무만 경고한다.
- 고른 Day가 아닌 Day의 장소는 그 Day의 시각을 모른다(계획 화면은 고른 Day만 계산한다). 그래서 날짜 판정(휴무·임시 휴무)만 하고 칩 아래에 `시각은 Day <N>을 고르면 확인해요`를 보인다.
- 그날 규칙이 휴무면 `Day 2 · 10.21(수) · 휴무 — 정기휴무 (매주 수요일)`(설명이 없으면 `· 휴무`까지), 규칙이 없으면 `Day 2 · 10.21(수) · 확인 필요`.
- 자정을 넘는 끝 시각은 규칙 줄에서 `18:00~02:00(다음 날)`. 끝이 `24:00`이면 그대로 `24:00`. 경고 문구의 규칙 시각에는 그 시각이 방문 날짜(`X`, §3.2)의 다음 날일 때만 `(다음 날)`을 붙인다(`24:00`은 붙이지 않는다).
- 계산에 쓰지 않는 규칙(예: `day`가 `공휴일`)은 `공휴일 10:00~17:00`처럼 한 줄씩 보인다. 그 아래 `공휴일 영업시간은 계산에 넣지 않아요`.
- 항목이 둘 이상이면 첫 항목으로 계산하고 `다른 운영 시간도 있어요: <이름들>`.
- `다시 확인`은 서버 캐시까지 건너뛰고 새로 받는다(§4.3). 받는 동안 버튼은 `확인 중…`, 누를 수 없다. 끝나면 확인 날짜 줄이 바뀐다. 이 줄은 `aria-live="polite"`.

확인 필요일 때 카드:

| 이유 | 카드 문구(`영업시간 확인 필요 — ` 뒤) | `다시 확인` |
|---|---|---|
| 카카오·구글·핀 | `네이버 장소만 영업시간을 받아요` | 없음 |
| 네이버에 정보 없음 | `네이버에 영업시간이 없어요` + 확인 날짜 줄 | 있음 |
| 없는 장소(`NOT_FOUND`) | `네이버에서 장소를 찾지 못했어요` | 있음 |
| 서버 문제·시간 초과 | `영업시간을 받지 못했어요` | 있음 |
| 연결 실패 | `인터넷에 연결되지 않았어요` | 있음 |
| 그 요일 규칙이 없음 | 규칙 줄이 `확인 필요` | 있음 |

받은 적이 있는 장소를 다시 받다 실패하면 **옛 정보를 그대로 쓰고**(옛 확인 날짜와 함께) 실패 문구를 확인 날짜 줄 옆에 `· 새로 받지 못했어요`로 붙인다.

### 2.3 화면 크기

- 좁음(<768): 시간표는 일정 시트 안. 칩은 행 너비에서 줄바꿈된다(`overflowWrap: anywhere`). 카드는 지금처럼 화면 아래 전체 폭.
- 중간(768~1279)·넓음(≥1280): 시간표 칸과 지도 카드(최대 360px). 같은 조각을 쓴다. 따로 배치를 바꾸지 않는다.

### 2.4 문구 (이것만 새로 쓴다)

행·카드 경고(시각은 `formatClock` — 자정 뒤는 `다음 날 01:10`):

| 종류 | 문구 |
|---|---|
| 휴무일 | `휴무일 — <요일 설명>` (설명이 없으면 `휴무일`) |
| 임시 휴무 | `임시 휴무 — <원문>` |
| 영업 전 | `<시각> 도착 — 영업 시작 <여는 시각>` |
| 영업 끝 | `<시각> 도착 — 영업 종료 <닫는 시각>` |
| 브레이크타임 | `<시각> 도착 — 브레이크타임 <시작>~<끝>` |
| 라스트오더 | `<시각> 도착 — 라스트오더 <시각>` |
| 머무는 중 영업 끝 | `머무는 중 영업 종료 <닫는 시각>` |
| 머무는 중 브레이크타임 | `머무는 중 브레이크타임 <시작>~<끝>` |
| 모름 | `영업시간 확인 필요` |

- 고정 시각까지 기다렸다 시작하는 장소는 `도착` 대신 `시작`(`11:00 시작 — …`). 판정도 그 시각으로 한다.
- 카드 문구: `영업시간`, `확인 중…`, `다시 확인`, `<M>월 <D>일 확인 · 네이버`, `· 새로 받지 못했어요`, `브레이크타임`, `라스트오더`, `휴무`, `확인 필요`, `네이버 안내: `, `다가오는 임시 휴무: `, `정기 휴무: `, `다른 운영 시간도 있어요: `, `공휴일 영업시간은 계산에 넣지 않아요`, `시각은 Day <N>을 고르면 확인해요`, §2.2 표의 이유 다섯.

## 3. 판정 규칙

### 3.1 그날 규칙 고르기

- 날짜 → 요일은 `YYYY-MM-DD`를 UTC 자정으로 읽어 `getUTCDay()`(기기 시간대와 무관).
- 요일 규칙: 그 요일(`월`~`일`) 항목, 없으면 `매일` 항목. 둘 다 없으면 **모름**.
- `평일`·`주말`·`공휴일`·범위(`월~금`) 같은 다른 표기는 본 적이 없어 계산하지 않는다(카드에 글로만, §2.2). 실제로 나오는 것을 확인하면 그때 더한다.
- 규칙이 `closed`면 **휴무일**. `closed`가 아닌데 `open`이 없으면 **모름**.

### 3.2 시각과 자정

- Day 축(그날 0시 = 0분)에서 계산한다. 방문 시작 `S`(고정 시각을 기다리면 `max(도착, 고정)`, 아니면 도착)와 끝 `E`(=`departMin`).
- `S`가 들어가는 날짜 `X = Day 날짜 + floor(S / 1440)`. **`X-1`·`X`·`X+1` 세 날**의 규칙 구간을 Day 축의 분으로 옮겨 함께 본다. `X-1`은 전날 밤 영업의 자정 넘은 부분 때문에, `X+1`은 머무는 동안 자정을 넘겨 다음 날 영업으로 이어지는지(24시간 영업 등) 보려고 넣는다. 세 날 모두 요일 규칙으로 고르고(§3.1), 휴무·모름인 날은 구간을 만들지 않는다.
- 끝 시각 `24:00`은 1440분. 끝 ≤ 시작이거나 `endsNextDay`면 끝에 1440을 더한다.
- 끝과 시작이 맞닿는 구간(앞 구간 끝 = 다음 구간 시작. `24:00`은 다음 날 `00:00`과 같은 분이다. 예: 매일 00:00~24:00)은 하나로 이어 붙인다(24시간 영업이 자정마다 끊기지 않게). 예: Day 날짜 = `X`, `매일 00:00~24:00`이면 `X-1` [-1440, 0], `X` [0, 1440], `X+1` [1440, 2880] → [-1440, 2880] 하나. 23:30 도착(`S` 1410)·다음 날 00:30 떠남(`E` 1470)은 그 안이라 문제없음(`X+1`을 빼면 [-1440, 1440]에서 `E`가 넘어 "머무는 중 영업 종료"로 잘못 나온다).
- **하루 경계** `DAY_ROLLOVER_HOUR`(04:00): F5 당일 모드의 새벽 경계와 같은 값·같은 상수다(F5 `src/domain/trips/today.ts`의 `DAY_ROLLOVER_HOUR = 4`를 F6이 import해 함께 쓴다 — §10). 방문일 `X`의 경계 분 `B = (X - Day 날짜) × 1440 + DAY_ROLLOVER_HOUR × 60`. §3.3의 4번이 "새벽 도착이 전날 밤 영업의 끝 뒤인가, 그날 영업 전인가"를 이 경계로 가른다.
- 브레이크타임·라스트오더도 그 규칙의 날짜 기준으로 같은 방법으로 옮긴다.
- 시간대: 네이버 영업시간과 앱의 시각은 모두 한국 현지 시각이다. 장소 좌표가 한국으로 제한돼 있어(`Lng`·`Lat`) 바꾸지 않는다. 확인 날짜만 기기 시간대로 보인다(경로의 `queriedLabel`과 같다).

### 3.3 판정

1. 그날 임시 휴무 원문 안에 그 날짜가 있으면(§3.6) → **임시 휴무**.
2. 그날 규칙이 휴무이고 전날 자정 넘은 구간에도 `S`가 없으면 → **휴무일**.
3. 규칙이 모름이고 전날 자정 넘은 구간에도 `S`가 없으면 → **모름**(구간 안이면 그 구간으로 5~9를 본다).
4. `S`가 어느 영업 구간에도 없으면 하루 경계 `B`(§3.2, 방문일 04:00)로 가른다.
   - `S < B`(04:00 전, 새벽): `S` 전에 끝난 구간이 있으면 **영업 끝**(그중 가장 늦게 끝난 구간의 끝 — 전날 밤 영업의 끝), 없으면 **영업 전**(`S` 뒤 첫 구간의 시작).
   - `S ≥ B`(04:00부터): `B`와 `S` 사이에 시작한 구간이 없으면(그날 첫 영업 시작 전) **영업 전**(`S` 뒤 첫 구간의 시작). 있으면(그날 영업이 끝났거나 두 구간 사이) **영업 끝**(`S` 전에 끝난 가장 늦은 구간의 끝).
   - 예(`매일 18:00~02:00`): 02:30 → 영업 끝 02:00, 03:59 → 영업 끝 02:00, 04:00 → 영업 전 18:00, 10:00 → 영업 전 18:00. 예전 규칙("0시부터 `S` 사이에 끝난 구간이 있으면 영업 끝")은 10:00도 02:00에 끝난 구간 때문에 영업 끝이 되는 잘못이 있어 고쳤다.
5. `S`가 브레이크타임 안이면 → **브레이크타임**.
6. `S`가 들어간 토막(영업 구간을 브레이크타임으로 나눈 조각) 안에 라스트오더가 있고 `S` > 라스트오더면 → **라스트오더**.
7. `E` > 그 구간 끝 → **머무는 중 영업 끝**.
8. `S` < 브레이크 시작 < `E` → **머무는 중 브레이크타임**.
9. 그 밖 → 문제없음.

### 3.4 우선순위

한 행에는 위 순서에서 먼저 걸린 것 하나만 보인다. 받은 정보는 바뀌지 않으므로, 순서·시간을 바꾸면 화면이 다시 그려질 때 다시 판정한다(요청 없음).

### 3.5 공휴일

공휴일 달력을 넣지 않는다. 공휴일이라도 그 요일 규칙으로 판정한다. 네이버가 `공휴일` 항목을 주면 카드에 글로 보이고 `공휴일 영업시간은 계산에 넣지 않아요`를 붙인다. 다른 방법은 §12-4.

### 3.6 임시 휴무 원문 맞추기

형식을 본 적이 없다(§1.4). 서버는 `comingIrregularClosedDays`의 문자열 항목을 원문으로 넘기고, 객체 항목은 문자열 값만 이어 붙인 글로 넘긴다. 앱은 원문에서 `YYYY-MM-DD`, `YYYY.MM.DD`, `YYYY.M.D`, `YYYY년 M월 D일`, `M월 D일`(연도 없으면 그날 연도) 꼴의 날짜를 뽑아(앞뒤에 숫자가 이어지면 날짜로 보지 않는다) 그 날짜와 같을 때만 임시 휴무로 본다. 날짜를 뽑지 못한 원문은 카드에 글로만 보인다.

## 4. 데이터

### 4.1 서버 응답 (`GET /api/hours`)

입력: `sid`(숫자 1~15자리, 아니면 400 `BAD_REQUEST`), `fresh=1`이면 엣지 캐시를 보지 않는다(새 결과는 같은 키에 저장). 출처 검사·오류 모양은 다른 함수와 같다.

```ts
/** 'HH:mm'. 끝 시각만 '24:00'이 올 수 있다. */
type HoursSpan = { start: string; end: string };
type HoursDay = {
  /** 네이버 표기 그대로('월'~'일', '매일', 그 밖도 그대로). */
  day: string;
  /** 휴무 요일·읽지 못한 시각은 null. */
  open: (HoursSpan & { endsNextDay: boolean }) | null;
  /** 네이버 시각이 null이고 설명에 '휴무'가 들어 있다. 시각을 못 읽었을 뿐이면 false(→ 모름). */
  closed: boolean;
  breaks: HoursSpan[];
  /** 라스트오더 시각들(읽을 수 있는 것만). */
  lastOrders: string[];
  /** 예: '정기휴무 (매주 수요일)'. */
  note: string | null;
};
type PlaceHours = {
  sid: string;
  /** 서버가 네이버에서 받은 시각(ISO). 엣지 캐시에서 나와도 처음 받은 시각 그대로다. */
  fetchedAt: string;
  /** 첫 운영 시간 항목. 네이버에 영업시간이 없으면 빈 배열. */
  days: HoursDay[];
  irregularClosed: string[];
  regularClosed: string | null;
  /** freeText. 빈 문자열은 null. */
  note: string | null;
  /** 둘째 항목부터의 이름(빈 이름은 뺀다). */
  otherSchedules: string[];
};
```

- 성공 200 `PlaceHours`. `newBusinessHours`가 `null`·`[]`이면 `days: []`(정보 없음)로 성공이다 — 정상 답이라 캐시한다.
- `__APOLLO_STATE__`나 `"newBusinessHours":`가 HTML에 없으면 502 `UPSTREAM_ERROR`(요청이 막혀 빈 페이지가 왔을 수 있다 — 캐시하지 않는다). 네이버 404는 404 `NOT_FOUND`.
- 이동(3xx)은 2번까지 따라간다. 대상은 `https://pcmap.place.naver.com/<영문 소문자>/<같은 sid>/home`만(쿼리는 버린다). 그 밖은 502.
- 엣지 캐시 1일(`max-age=86400`), 키 `https://cache.landmark/hours/naver/<sid>`.

### 4.2 저장 위치 (C6 — 이 묶음이 정함)

**보관함 밖의 기기 캐시** `localStorage['tripmap:hours:v1']` = `{ entries: { [sid]: PlaceHours & { usedAt: string } } }`.

- 최대 300곳, 직렬화 400,000자. 넘으면 `usedAt`이 오래된 것부터 지운다. 쓰기 실패면 오래된 절반을 지우고 한 번 더, 그래도 실패하면 그 세션은 메모리만.
- 읽을 때 항목마다 모양을 검사해 틀린 항목만 버린다. 문서가 깨졌으면 빈 캐시.
- 보관함 저장이 용량을 넘으면 경로 캐시와 함께 이 캐시도 지우고 다시 쓴다(보관함이 우선, 영업시간은 다시 받으면 된다). F1이 그 뒤에 둔 단계(그래도 넘치면 되살리기 전 사본 `tripmap:library:v2:before-restore`를 지우고 한 번 더 — F1 설계서 §3.3)는 그대로 둔다. 순서: 경로·영업시간 캐시 → 되살리기 전 사본.

장소 필드(`PlaceSchema`)에 넣지 않는 이유:

1. **옛 버전이 지운다.** `LibraryStore.update`는 읽은 문서를 `LibrarySchema`로 다시 디코드한 뒤 저장한다. Effect 4.0.2의 디코드 기본값은 `onExcessProperty: "ignore"` — 모르는 키를 **버린다**(`node_modules/effect/src/SchemaAST.ts` 490행 주석 `"ignore" (default) strips unknown object keys`, `parse.ts`의 `safeParse`는 이 값을 바꾸지 않는다). 그래서 `v0.12.0`에서 아무 편집이나 하면 영업 정보가 사라진다(손상 화면은 뜨지 않는다).
2. **용량.** 한 곳에 약 1~1.5KB. 보관함 상한이 400만 자인데 저장 장소가 1,000곳이면 1~1.5MB를 바깥 정보가 차지한다.
3. **LWW가 맞지 않는다.** 바깥에서 받은 값은 기기마다 다시 받으면 되고, 편집 충돌을 가릴 일이 없다.

그래서 백업(C3)·공유(C4)에도 들어가지 않는다(다시 받는 캐시 — 경로 캐시와 같다).

### 4.3 언제 다시 받나

| 때 | 동작 |
|---|---|
| 계획 화면을 열거나 Day의 장소가 바뀜 | 그 여행 모든 Day의 네이버 장소 중 캐시에 없거나 `fetchedAt`이 **7일** 넘은 것만 요청(고른 Day 먼저) |
| 후보의 카드를 엶 | 그 장소 하나(같은 규칙) |
| 카드 `다시 확인` | 그 장소를 `fresh=1`로 |
| 연결 실패였던 장소 | 브라우저 `online` 이벤트 때 다시 |
| 서버 문제·시간 초과·없음 | 이 세션에서는 자동으로 다시 묻지 않는다(`다시 확인`으로) |

- 7일 넘은 정보도 새로 받기 전까지는 그대로 판정에 쓰고 확인 날짜를 보인다.
- 동시에 서버에 보내는 요청은 **2개**(네이버 장소 홈은 무겁고, 잦으면 빈 응답이 온다). 같은 sid 요청은 하나로 합친다. 앱 쪽 시한 12초.

### 4.4 호환·롤백

- 보관함(`tripmap:library:v2`, `schemaVersion` 2)·`tripmap:prefs`·`tripmap:routes:v1`·공유 형식은 그대로다.
- `v0.12.0` 이하로 되돌리면 그 버전은 `tripmap:hours:v1`을 모른다. 읽지 않고 지우지도 않는다(용량만 조금 차지). 다시 `v0.13.0`으로 오면 그대로 쓴다. ✅

## 6. 오류 처리

- 서버: 모르는 모양은 던지지 않고 정규화에서 버린다 — 시각 꼴이 아니면 그 요일 `open: null`·`closed: false`(→ 앱은 모름), 원문 `note`는 남긴다. 휴무는 네이버 시각이 `null`이고 설명에 `휴무`가 있을 때만. 배열이 아닌 `breakHours`·`lastOrderTimes`는 빈 배열, 시각 꼴이 아닌 항목은 뺀다.
- 서버: 괄호 맞추기는 문자열 안의 괄호·이스케이프를 건너뛴다. 끝을 못 찾거나 JSON이 아니면 502.
- 앱: 서버 응답 처리 규칙은 `RouteLookup`과 같다(HTML·`error` 없는 404·네트워크 실패는 `OFFLINE`, 5xx HTML은 `UPSTREAM_ERROR`, 응답 모양 검사 실패는 `UPSTREAM_ERROR`). 콘솔 경고는 세션에 한 번.
- 앱: 판정 함수는 어떤 입력에도 던지지 않는다. 읽을 수 없으면 모름.

- `server/hours`: 녹화 HTML 조각 두 개(단천면옥 11733192 — 수요일 정기휴무·브레이크·라스트오더, 88생선구이 11815720 — `매일`·freeText)와 손으로 만든 조각(자정 넘김, `null`, `[]`, 키 없음, 깨진 JSON, 문자열 안의 `]`)의 정규화. 302 → `/restaurant/…` 이동 따라가기, 다른 호스트·다른 sid로 이동은 502, 404 → `NOT_FOUND`.

- `domain/trips/hours`: §3의 각 판정, 요일 고르기(`매일`·없음), `24:00`, 자정 넘김(전날 구간에 다음 날 01:00 도착), 24시간 이어 붙이기(`X+1`까지 — 23:30~다음 날 00:30 체류가 `ok`), 하루 경계(`18:00~02:00`의 03:59 → 영업 끝, 04:00 → 영업 전), 다음 날 도착(`arriveMin` ≥ 1440)의 요일, 고정 시각 기다림(`시작`), 라스트오더 두 개(점심·저녁), 임시 휴무 날짜 꼴 넷, 모르는 `day` 표기, 우선순위, 문구가 §2.4와 글자까지 같음.
- `services/hours-lookup`: 캐시 적중(7일 안)·7일 넘으면 요청·`refresh`면 `fresh=1`, 같은 sid 합치기, 동시 2개, 300곳·40만 자 넘으면 오래된 것부터, 깨진 저장값, 응답 모양 검사, 오류 코드 변환.
- `library-store`: 용량 초과 때 영업시간 캐시도 지우고 다시 씀.
- 화면: 행에 칩·확인 필요·없음, 카드의 규칙 줄·확인 날짜·`다시 확인`(누르면 `fresh=1`, 받는 중 `확인 중…`), 다른 Day의 장소 안내, 카카오 장소 이유 문구.

E2E(Playwright, 세 프로젝트): `/api/hours`를 녹화 응답으로 대신한다(`매일 10:00~20:00` 응답). 강릉 여행에 장소를 넣으면 첫 행에 `09:00 도착 — 영업 시작 10:00`, 카드에 `확인 · 네이버`와 `다시 확인`, 출발 시각을 10:30으로 바꾸면 칩이 사라짐. `/api/hours`를 막은 기존 계획 시험은 그대로 통과(행에 `영업시간 확인 필요`만 더해진다).

## 8. 첫 로딩 예산

- 화면 조각·판정은 계획 화면 덩어리(`TripPlannerPage`, 이미 `--require-lazy`)에만 들어간다.
- 첫 로딩에 붙는 것은 `AppLayer`에 들어가는 `HoursLookup`(경로 조회와 비슷한 크기)과 `HoursLookupError`뿐이다. 2026-10-14 측정 297,769 / 예산 327,680. F1~F5 뒤의 여유는 확인 필요 — 마지막 작업에서 `yarn build:ci`로 잰다. 넘으면 `HoursLookup`을 계획 화면에서만 제공하는 레이어로 옮긴다.

## 9. 접근성

- 경고는 색만이 아니라 글로 말한다(아이콘은 `aria-hidden`). 칩 색은 이미 여섯 테마 AA 검사를 받는 라벨 주황 짝(`label.orange.text` / `label.orange.fill`)을 쓴다 — 새 토큰 없음.
- 행 안의 칩은 행 버튼의 이름에 함께 읽힌다(체류·고정 줄과 같다).
- 카드 `다시 확인`: 44px, 이름 그대로. 받는 동안 포커스를 지닌 채 `aria-disabled`(누름 무시)와 `확인 중…`. 확인 날짜 줄은 `aria-live="polite"`이고, 누른 뒤 새로 받으면 보이지 않는 ` · 확인했어요`를 붙여 같은 날이어도 알린다.
- 카드 제목 구조: 카드의 `h2`(장소 이름) 아래 `h3 영업시간`. 화면별 `h1` 하나는 그대로.
- 포커스 표시·입력칸은 기존 테마를 따른다(새 입력칸 없음).

## 10. 묶음 사이 약속

- **C6(이 묶음이 주인)**: 영업 정보는 보관함 밖 `tripmap:hours:v1`(§4.2). `PlaceSchema`에 필드를 더하지 않는다. 다른 묶음이 쓸 이름: `HOURS_CACHE_KEY`, `PlaceHours`(`src/server/hours.ts`), `checkVisit`·`visitMessage`(`src/domain/trips/hours.ts`), `usePlaceHours`, `HoursNotice`.
- C1(다녀옴·한 줄 평): 관계없음. 다녀온 장소도 같은 경고.
- C2(내 위치): 쓰지 않음.
- C3(백업): `tripmap:hours:v1`은 백업에 넣지 않는다(경로 캐시처럼 다시 받는 캐시). F1 설계서 초안도 같은 뜻이라 F1이 할 일은 없다.
- C4(공유): 공유 파일에 영업 정보를 넣지 않는다. F7 보기 화면은 경고를 보이지 않는다.
- C5(폴더 기록): 관계없음.
- F5(당일 모드): F5는 F6에 기대지 않는다. F6도 F5 화면을 고치지 않는다(§12-5). 단, 하루 경계는 F5의 상수 `DAY_ROLLOVER_HOUR`(`src/domain/trips/today.ts`, 값 4)를 import해 같은 값을 쓴다(§3.2, 값이 둘로 갈라지지 않게). F6이 F5 코드에 기대는 곳은 이 하나뿐이다. 그래서 F5만 되돌리려면 F6을 먼저 되돌린다(또는 이 상수를 F6 쪽으로 옮긴다).

## 12. 결정이 필요한 것

1. **영업 정보 저장 위치(C6)** — 선택지: (가) 보관함 밖 기기 캐시 `tripmap:hours:v1` / (나) `PlaceSchema` 선택 필드(확인 시각 포함) / (다) 저장 없이 매번 서버. 추천 (가). 이유: 저장 형식이 그대로라 롤백이 안전하고(나는 옛 버전이 저장할 때 필드를 지운다 — §4.2), 보관함 용량을 쓰지 않고, 화면을 열자마자 지난번 정보로 경고가 뜬다(다는 연결이 없으면 아무것도 모른다).
2. **다시 받는 주기** — 선택지: 7일 / 1일 / 직접 `다시 확인`할 때만. 추천 7일. 이유: 영업시간은 자주 바뀌지 않고, 네이버 요청을 아껴야 한다(잦으면 빈 응답). 임시 휴무는 출발 직전에 `다시 확인`으로.
3. **정보 없는 장소의 행 표시** — 선택지: 행·카드 모두 `영업시간 확인 필요` / 카드에만. 추천 행·카드 모두. 이유: "모르면 확인 필요로 남긴다"는 원칙. 해변·공원처럼 원래 시간이 없는 곳에도 붙어 시끄러울 수 있다 — 써 보고 카드에만으로 줄일 수 있다(행 조각 하나만 바뀐다).
4. **공휴일** — 선택지: (가) 계산하지 않고 카드에 규칙만 / (나) 공휴일 표를 코드에 넣기(해마다 대체·임시 공휴일 갱신 필요) / (다) Day에 `공휴일` 표시를 두기(여행 저장 형식 변경). 추천 (가). 이유: 근거 없는 추측을 피하고 형식을 바꾸지 않는다. `공휴일` 표기가 실제로 오는지도 아직 모른다.
5. **당일 모드(F5)에 경고** — 선택지: 이번에 넣지 않고 F5 병합 뒤 작은 후속(지금·다음 장소 카드에 `HoursNotice` 한 줄) / 이번에 넣기. 추천 후속. 이유: F5 설계서(2026-10-16 초안 §C6 표)가 자리를 "카드의 줄 1 뒤, 남은 일정 행의 시각 줄 뒤"로 비워 두었지만, F5 구현이 끝나기 전에는 파일·이름이 바뀔 수 있다. 필요한 조각(`usePlaceHours`·`noticeFor`·`HoursNotice`·`checkVisit`)은 이번에 내보낸다. 이 경우 당일 모드는 계획 화면을 열어 받아 둔 캐시만 쓰고, 없으면 그 장소 하나를 묻는다(`usePlaceHours(place, { request: true })`).

9. **Cloudflare에서 네이버 장소 홈이 막힐 때** — 선택지: 그대로 `확인 필요` / 앱(브라우저)이 직접 받기(CORS로 막힘 — 불가) / 다른 원천. 추천 그대로 `확인 필요`, 미리보기 배포에서 먼저 확인(계획 마지막 작업). 막히면 이 묶음을 병합하지 않고 다시 논의한다.
10. **"영업 끝"과 "영업 전"을 가르는 하루 경계** (리뷰 반영으로 더함) — 영업 구간 밖 도착을 새벽이면 전날 밤 영업의 끝 뒤로, 그 뒤면 그날 영업 전으로 본다(§3.3-4). 선택지: (가) 04:00, F5 `DAY_ROLLOVER_HOUR`를 함께 씀 / (나) 05:00·06:00 같은 다른 값(F6만의 상수) / (다) 경계 없이 "그날 첫 영업 시작 전이면 영업 전"만. 추천 (가). 이유: 당일 모드가 "04:00 전은 어제"로 보는 것과 같은 하루라 두 화면의 말이 어긋나지 않는다. 한 상수라 바꿀 때 함께 바뀐다.
