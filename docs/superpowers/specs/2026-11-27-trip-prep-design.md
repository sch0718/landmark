# 여행 준비(예약·기초 정보·현지어 문장) 기획

- 상태: 승인(2026-11-27). 결정 4개는 모두 추천안(1가·2가·3가·4가)으로 정했다(§7).
- 작성: 2026-11-27
- 전제: 사용자 1명(+함께 가는 사람)이 여러 기기에서 쓰는 개인 PWA. Cloudflare 무료, 앱 안에서 유료 API·LLM을 부르지 않는다. 판단이 갈리면 작은 쪽을 고른다.
- 첫 실사용: 이베리아 여행(2026-12-19 ~ 12-31, 파리·세비야·바르셀로나). 오늘부터 3주 남았다.

## 1. 요약

- 여행마다 `준비` 화면(`/trips/:id/prep`)을 하나 더 두고, 그 안에 **예약 · 정보 · 문장** 세 탭을 둔다.
- 저장은 여행(`Trip`) 문서의 **선택 필드 세 개**(`bookings`·`prepNotes`·`phrases`)로 한다. 새 항목 종류나 서버 테이블을 만들지 않는다. 그래서 동기화·백업·AI 편집(`yarn trip library put`)은 지금 장치를 그대로 탄다.
- 예약번호 같은 개인 정보는 **공유 링크·갱신 링크·함께 편집에 들어가지 않는다.** 공유 문서는 필드를 하나씩 골라 만들기 때문에, 새 필드는 따로 넣지 않는 한 빠진다.
- 내용은 주로 **사용자와 AI 도구가 채운다.** 앱이 외부 API(환율·날씨)를 직접 부를지는 사용자 결정으로 남긴다(§7). 추천은 「첫 버전에서는 부르지 않음」이다.
- 발음 듣기는 브라우저 내장 `speechSynthesis`를 쓴다. 번들이 늘지 않고 비용도 0이다. 기기에 그 언어의 음성이 없으면 구글 번역 링크로 대신한다.
- 첫 버전은 PR 두 개로 나눈다. ① 예약(저장 형식 포함), ② 정보·문장·발음. 둘 다 12월 19일 출발 전에 써 볼 수 있다.

## 2. 이미 있는 것과 겹치는 부분

| 필요 | 지금 있는 것 | 왜 그것으로는 안 되나 |
|---|---|---|
| 예약 현황 | Stop `note`(500자), 장소 `memo` | 상태·금액·기한을 모아 볼 수 없다. 항공·기차·여행자 보험처럼 장소가 아닌 예약은 붙일 곳이 없다. |
| 기초 정보 | 없음(여행 단위 메모가 없다) | 장소 메모는 장소 하나에 붙는다. 「스페인의 팁 문화」 같은 여행 전체 정보를 둘 곳이 없다. |
| 현지어 문장 | 없음 | 메모에 적을 수는 있지만 상황별로 고르거나 발음을 들을 수 없다. |
| 숙소에 보낼 메시지 | 없음 | 따로 만들지 않는다. 문장 탭의 「긴 문장」으로 둔다(§5.4). |

겹치지 않게 하는 원칙:

- **장소 하나에 대한 정보**(영업시간, 그 식당 메뉴 팁)는 지금처럼 장소 메모에 둔다. 준비 화면은 여행 전체에 걸친 것만 맡는다.
- **그날 일정의 메모**는 Stop `note`에 둔다. 예약 항목은 장소와 날짜로 이어 보일 뿐, 메모를 옮기지 않는다.

## 3. 고른 방식

| 방식 | 내용 | 판단 |
|---|---|---|
| A. 여행 메모 하나 | 여행에 긴 글 칸 하나만 더한다 | 가장 작지만 집계·필터·발음 듣기가 안 된다. 「한 곳에서 보기」라는 요청에 못 미친다. |
| **B. 여행 문서의 구조화된 선택 필드** | `Trip`에 `bookings`·`prepNotes`·`phrases`를 더한다 | **추천.** 기존 동기화(필드 단위 LWW)·백업·AI 편집 경로를 재사용한다. 보관함 스키마와 여행의 장소 참조 수집·정리에 예약을 포함한다(§4.1~§4.2). 공유 문서에는 넣지 않는다(§4.4). |
| C. 새 항목 종류 `prep`(나라 단위) | 여러 여행이 나라 정보를 같이 쓴다 | 다시 쓸 수 있다는 장점이 있지만 서버·동기화·백업에 새 종류를 더해야 한다. 여행이 자주 있지 않은 1인 전제에서는 과하다. 「다른 여행에서 가져오기」(§8 나중에)로 대신한다. |

## 4. 저장 형식

### 4.1 `Trip`에 더할 선택 필드

기존 `legTransit`·`legMinutes`와 같은 방식이다. `Schema.optional(FieldSchema(...))`로 두어 옛 문서도 그대로 읽힌다. 동기화 병합은 최상위 필드 단위 LWW를 따른다(`src/domain/library-sync/merge.ts`의 `mergeItem`). 두 기기가 같은 예약 목록을 각자 수정하면 변경 시각이 더 늦은 쪽의 목록으로 `bookings` 전체가 교체된다. 1인이 쓰는 앱에서는 드문 일이라 항목 단위 병합은 만들지 않는다.

예약 목록의 충돌은 이 기기에서 충돌 기준 시각(보통 지난 동기화 시각) 이후에 수정한 값이 병합에서 졌을 때만 기록한다(`src/domain/library-sync/apply.ts`의 `applyRemote`·`conflictsFor`). 이미 올린 뒤 추가 수정이 없는 기기는 다음 수신 때 목록이 바뀌어도 충돌을 기록하지 않는다. 충돌 목록은 최신 50건까지 보관하며, 직렬화 결과가 20만 자를 넘으면 오래된 기록부터 뺀다(`src/services/library-sync/storage.ts`의 `writeConflicts`). 따라서 충돌 목록에서 이전 예약 목록을 복구할 수 없는 경우가 있다.

```ts
// src/schema/trip.ts (구현 때 한도는 LIBRARY_LIMITS로)
const BookingKind = Literals(['flight', 'train', 'bus', 'lodging', 'ticket', 'restaurant', 'tour', 'car', 'insurance', 'other']);
const BookingNeed = Literals(['required', 'recommended', 'optional']);
const BookingStatus = Literals(['todo', 'booked', 'pending', 'skipped']); // 예약 전·예약함·결제 대기·안 하기로 함

const Booking = Struct({
  id: 8자 영숫자,
  kind: BookingKind,
  title: String 1~80,                 // 「사그라다 파밀리아 입장권」
  need: BookingNeed,
  status: BookingStatus,
  date: NullOr(CalendarDate),          // 쓰는 날(일정의 어느 날인지)
  placeId: NullOr(PlaceId),            // 일정의 장소·숙소와 이을 때
  links: Array(Struct({ label: String 0~30, url: https URL 500자 })) 0~3,
  bookBy: NullOr(CalendarDate),        // 이때까지 예약(매진 위험)
  at: NullOr(String "YYYY-MM-DDTHH:mm"), // 확정 일시(현지 시각, 시간대 없음)
  freeCancelUntil: NullOr(String "YYYY-MM-DDTHH:mm"),
  code: String 0~60,                   // 예약번호
  price: NullOr(Struct({ amount: Number ≥ 0, currency: 3자 대문자 })),
  bookedVia: String 0~40,              // 예약한 곳(사이트·앱)
  note: String 0~300,
});

const PrepNote = Struct({
  id: 8자,
  topic: Literals(['language', 'money', 'prices', 'weather', 'time', 'power', 'tips', 'safety', 'emergency', 'transit', 'docs', 'other']),
  region: String 0~30,                 // 「스페인」, 「파리」, 빈칸이면 여행 전체
  text: String 1~1500,
  sources: Array(https URL 500자) 0~3,
  checkedOn: NullOr(CalendarDate),     // 확인한 날
  unsure: Boolean,                     // 「확인 필요」 표시
});

const Phrase = Struct({
  id: 8자,
  situation: Literals(['greet', 'restaurant', 'directions', 'transit', 'lodging', 'shopping', 'emergency', 'other']),
  ko: String 1~200,
  text: String 1~500,                  // 현지어
  lang: BCP 47 2~12자,                 // 「es-ES」, 「fr-FR」
  reading: String 0~300,               // 한글 읽는 법
  note: String 0~200,
});

TripSchema += {
  bookings: Schema.optional(FieldSchema(Array(Booking) 0~60)),
  prepNotes: Schema.optional(FieldSchema(Array(PrepNote) 0~40)),
  phrases: Schema.optional(FieldSchema(Array(Phrase) 0~150)),
};
// 개수·글자 수와 별도로, 필드 하나의 직렬화 길이 상한(아래 「크기」)
```

- 관계 검증(`src/schema/trip.ts`의 `checkTrip`)에서 예약의 `null`이 아닌 `placeId`가 보관함에 있는지 확인한다. 장소가 일정에서 빠져 예약만 참조하는 경우에도 유효하며, 묘비를 허용한다. 각 배열 안의 `id` 중복도 검사한다. `date`는 검증하지 않는다. 여행 날짜를 옮겨도 저장이 깨지면 안 되기 때문이다. 기간 밖 날짜는 화면에서 「기간 밖」으로 표시한다.
- 크기: 동기화·AI CLI는 여행 문서 하나를 직렬화해 20만 자(`ITEM_DOC_MAX_CHARS`, `src/domain/library-sync/items.ts`)까지만 받는다. 이 상한은 옛 기기도 쓰므로 올리지 않는다. 대신 세 필드에 **직렬화 길이 상한**을 따로 두고 `checkTrip`에서 검사한다: `bookings` 5만 자, `prepNotes` 3만 자, `phrases` 3만 자(합계 11만 자). 그러면 일정 부분에 9만 자 이상이 남는다. 필드마다 상한이 따로라서, 병합이 두 사본의 필드를 섞어도 준비 필드 합계가 11만 자를 넘지 않는다. 실제 규모는 예약 30건·정보 15개·문장 60개 기준 약 4만 자로 본다.
- 일정이 아주 긴 여행이라 합계가 20만 자를 넘으면 앱은 준비 화면 저장을 막고 「여행 문서가 너무 커요」를 보인다(기존 동기화의 `too-large`와 같은 기준). 서버 `pushItems`는 병합 결과에도 같은 크기 검사를 하고, 넘으면 저장하지 않은 채 `too-large`로 응답한다. 저장된 사본은 그대로 남는다. 서버 변경은 이 검사 한 줄이다.
- 금액은 통화별로 따로 더한다. 환율로 바꿔 한 숫자로 합치는 일은 첫 버전에서 하지 않는다.

### 4.2 동기화·백업·되돌리기

- `src/domain/library-sync/items.ts`의 `tripRefs`에 `bookings?.value`의 `null`이 아닌 `placeId`를 더한다. `decodeItem`과 `src/domain/library-sync/merge.ts`의 `mergeItem`은 이 목록으로 `checkTrip`에 넘길 임시 장소 목록을 만든다. `src/server/library-sync/library.ts`는 같은 목록을 D1의 여행 행 `refs`에 저장하므로 `purgeTombstones`는 예약만 참조하는 장소 묘비도 보존한다.
- `src/domain/library-sync/repair.ts`의 `repairLibrary`가 중복 장소를 합칠 때, 사라지는 장소를 가리키는 예약의 `placeId`를 생존 장소 ID로 바꾸고 `bookings` 필드의 변경 시각을 갱신한다. 동기화 설계의 [중복 장소 참조 이전 규칙](2026-10-29-library-sync-design.md)을 따른다.

- `OPTIONAL_FIELD_EMPTY.trip`에 `bookings: []`, `prepNotes: []`, `phrases: []`를 더한다. 이렇게 해야 옛 기기가 이 필드를 빠뜨려 올려도 서버가 값을 남긴다(v0.37.1 규칙).
- `FIELDS_REFRESH`를 1 → 2로 올린다(선택 필드를 더할 때의 규칙).
- 계획 화면의 실행 취소(`src/domain/trips/undo.ts`)는 이 세 필드도 되돌리게 한다. 준비 화면에도 같은 실행 취소를 쓴다. 첫 항목 추가를 되돌리거나 마지막 항목을 지울 때는 키를 없애지 않고 빈 배열 `[]`과 새 시각을 남긴다(`legTransit`·`legMinutes`와 같은 규칙). 키를 없애면 서버가 「옛 기기가 빠뜨린 것」으로 보고 옛 값을 지키기 때문이다.
- 백업 파일은 보관함 전체를 담으므로 그대로 들어간다.
- **동기화를 켜면 예약번호·금액이 서버(D1)에도 저장된다.** 이미 장소 메모 등 보관함 전체가 올라가므로 새 종류의 저장은 아니다. 다만 개인정보 처리방침의 「저장 항목」에 「여행 준비(예약·메모)」를 한 줄 더한다.

### 4.3 옛 버전·롤백(`docs/rollback.md`)

- 옛 앱(이 기능 전)은 세 필드를 떼어 내고 읽으므로 보관함은 손상 화면 없이 열린다. 읽기만 하면 저장 원문은 남는다. **장소 메모 하나만 저장해도** `src/services/library-store.ts`의 `update`가 보관함 전체를 다시 쓰므로 그 기기에 있는 **모든 여행**에서 `bookings`·`prepNotes`·`phrases`가 사라진다. 1단계 배포 때 롤백 표의 마지막 칸에 이 범위를 ⚠️로 적고 아래 절차를 연결한다.
- 새 서버는 옛 앱이 빠뜨린 준비 필드를 §4.2의 `keepMissingFields` 규칙으로 유지한다. 서버도 되돌리면 열려 있던 새 앱이 올린 여행에서 옛 서버가 세 필드를 떼고, 같은 `baseRev`의 문서를 저장한 뒤 결과 문서 없이 성공을 응답할 수 있다(`src/server/library-sync/library.ts`의 `pushItems`). 새 앱의 `applyPushResults`(`src/domain/library-sync/apply.ts`)는 그런 응답에서 보낸 문서를 동기화 기준으로 기록하므로, 성공 표시만 보고 서버에 필드가 남았다고 판단할 수 없다.
- `schemaVersion`(2)은 바꾸지 않는다.

1. **롤백 전.** 새 앱에서 각 기기의 설정 › 동기화를 열어 올리지 않은 변경, 충돌, 넣지 못한 항목, 올리지 못한 항목을 확인한다. 새 서버가 정상이라면 `지금 동기화`로 먼저 맞춘다. 맞추지 못한 변경이 있는 기기를 기록하고, 각 기기에서 설정 › 백업 › `백업 파일 받기`로 저장 원문을 담은 보관함 백업을 따로 보관한다(`src/sections/backup/use-backup-file.ts`).
2. **쓰기 중단.** 옛 버전을 배포하기 전에 동기화를 쓰던 기기마다 `동기화 끄기`를 누르고 열려 있는 앱 탭과 PWA를 닫는다. 옛 앱에서는 보관함을 읽기만 하고, AI 도구의 보관함 편집도 멈춘다. 서버까지 되돌릴 때는 옛 배포에서도 [`LIBRARY_SYNC=off`](../../development.md#보관함-동기화-설정과-api)로 받기·올리기를 막고, `AGENT_EDIT=off`로 AI의 `library edit`·`undo`도 막는다(`LIBRARY_SYNC=off`만으로는 AI 편집이 막히지 않는다, `src/server/agent/router.ts`). 3단계의 `library put` 전에 새 배포에서 다시 켠다.
3. **복구.** 준비 필드를 읽는 앱과 서버를 다시 배포한 뒤, 기기의 동기화를 끈 채 백업과 대조해 빠진 값과 미동기화 변경을 확인한다. 보관함 전체를 되살려야 하는 기기는 새 앱의 `백업 파일로 되살리기`를 사용한다. 백업이 여러 개면 기기별 변경을 확인한 뒤 복구할 값을 모은다. 서버에서 사라진 준비 필드는 §4.5의 `yarn trip library get trip <id>`로 현재 문서와 rev를 확인하고, 그 문서에 복구할 필드를 반영해 `yarn trip library put trip <id> --file <파일> --base-rev <rev>`로 올린다. 다시 `get`으로 세 필드가 서버에 있는지 확인한다.
4. **수신 확인.** 새 서버에서 받기·올리기를 다시 열고, 새 앱에서 한 기기씩 동기화를 다시 켜고 `지금 동기화`를 실행한다. 다른 기기의 준비 화면에서 복구한 값이 들어왔는지 확인하고, 충돌이나 올리지 못한 변경이 있으면 백업과 대조해 처리한 뒤 편집을 재개한다.

### 4.4 공유·갱신 링크·함께 편집

- 공유 v3·갱신 링크(`LiveTripDoc`)·함께 편집은 `ShareTripDoc`을 필드 하나씩 골라 만들고, `parseLiveDoc`은 키를 정확히 검사한다. 그래서 새 필드는 **따로 넣지 않는 한 나가지 않는다.** 이번 기능에서는 넣지 않는다.
- 함께 편집으로 받은 변경은 `src/domain/trip-collab/apply.ts`가 기존 여행을 펼쳐(`...trip`) 고치므로 새 필드가 남는다(확인함). 초대받은 사람 쪽에서 새로 만드는 여행은 빈 값으로 시작하므로 예약이 넘어가지 않는다. 앞의 경로를 지키는 시험을 하나 둔다.
- 함께 가는 사람에게 예약 내용을 보여 주는 일은 나중에 검토한다(§8). 보여 주더라도 예약번호는 빼고 상태·날짜·링크만 내보낸다.

### 4.5 AI 도구 연결

- AI는 이미 `yarn trip library get/put trip <id>`로 여행 문서를 고칠 수 있다(v0.32.0, `baseRev` 충돌 검사·되돌리기). 서버는 같은 `TripSchema`로 검사하고, `src/server/agent/library-edit.ts`의 `editItems`는 §4.2의 `tripRefs`로 예약이 가리키는 장소 행도 조회한다. **CLI 코드를 바꾸지 않아도** AI가 세 필드를 채울 수 있다.
- **옛 체크아웃의 CLI 보호.** CLI는 로컬 스키마로 문서를 디코딩해 보내므로(`pipeline/agent-trip/run-library.ts`), 이 기능 전 체크아웃으로 여행 제목만 고쳐도 세 필드가 빠진 채 올라간다. 지금 서버는 AI `put`에서 빠진 선택 필드를 「지우려는 뜻」으로 보고 빈 값으로 채운다(`src/server/agent/library-edit.ts`의 `emptyMissingFields`). 준비 필드에는 이 규칙을 적용하지 않는다. AI `put`에서 빠진 준비 필드는 **서버 값을 그대로 두고**, 지우려면 `[]`를 명시해야 한다. 구현은 `put` 경로에서만 `emptyMissingFields`가 이 세 키를 건너뛰게 하는 것이다. **AI 변경 되돌리기(`undoChanges`)는 지금 규칙을 그대로 쓴다.** AI가 처음 넣은 준비 필드를 되돌리면 `[]`과 새 시각으로 복원해야 서버에서 실제로 지워지기 때문이다(같은 함수를 공유하므로 호출하는 쪽에서 구분한다). 거절보다 이쪽을 고른 이유: 옛 체크아웃으로 다른 필드를 고치는 일을 막지 않고, 데이터도 남는다.
- CLI 안내를 보완한다. `yarn trip --help`의 `library` 절과 `docs/development.md`의 AI 절에 「준비 필드 예시 JSON」을 짧게 둔다. AI가 조사해 채울 때 `sources`·`checkedOn`·`unsure`를 꼭 쓰라고 적는다.
- `plan.json`(`yarn trip build`)은 공유 문서를 만드는 길이라 넓히지 않는다. 공유에는 준비 필드가 나가지 않기 때문이다.
- 이베리아 여행에서는 사용자가 만든 「이베리아 예약·준비장」의 예약 항목과 도시 정보를 AI가 `library put`으로 옮겨 담으면, 첫날부터 채워진 상태로 쓸 수 있다.

### 5.2 예약 탭

```
┌ 이베리아 여행 · 준비 ───────────── ✕ ┐

│ 예약함 7 / 12   ▓▓▓▓▓▓▓░░░░          │

│                                       │
│ 지금 예약할 것                         │
│ ! 알람브라 입장권   ~12/01 · 필수   [열기] │
│ ! 사그라다 파밀리아 ~12/05 · 필수   [열기] │
│                                       │
│ (전체) (할 것만) (아직 안 한 것)       │
│ ── 12/19 (토) ───────────────────── │

│ ── 12/22 (화) ───────────────────── │

│                          [＋ 예약 더하기] │
└───────────────────────────────────────┘
```

- 집계 규칙(상태별):

  | 상태 | 진행률 분자 | 진행률 분모 | 필수인데 아직 | 금액 합계 | `할 것만` | `아직 안 한 것` |
  |---|---|---|---|---|---|---|
  | `booked` 예약함 | ○ | ○ | | ○ | ○ | |
  | `pending` 결제 대기 | | ○ | ○(필수일 때) | ○ | ○ | ○ |
  | `todo` 예약 전 | | ○ | ○(필수일 때) | ○(금액을 적었으면 예상액) | ○ | ○ |
  | `skipped` 안 하기로 함 | | | | | | |

  `전체`는 네 상태를 모두 보인다. 안 하기로 한 예약은 분모·합계에서 빼야 「남은 일」이 정확하다. 금액은 통화별로 따로 더한다.
- 「지금 예약할 것」: `todo`·`pending` 가운데 `bookBy`가 있는 것을 최대 5개 보인다. 순서는 필수 먼저, 그 안에서 기한이 빠른 순이다. 기기 달력 날짜로 `bookBy`가 지났으면 빨간 표시를 한다. `[열기]`는 첫 링크를 새 탭으로 열고, 링크가 없으면 `[열기]` 대신 편집 시트를 여는 `[적기]`를 둔다.
- 목록은 `date` 순으로 묶고 `날짜 없음`을 맨 끝에 둔다.
- 날짜 기준: `date`는 사용자가 정한 일정일이다. 여행 기간을 바꿔도 `date`·`at`은 바꾸지 않고 「기간 밖」으로 표시한다. `at`·`freeCancelUntil`은 적은 그대로 현지 시각으로 보인다(시간대 변환을 하지 않는다). 확정 일시를 처음 적으면 `date`가 비어 있을 때만 그 날짜로 채운다.
- 항목을 누르면 아래쪽 시트(기존 휴대폰 시트 패턴)로 편집한다. 칸 순서: 상태(네 칩) → 제목·종류·필요도 → 날짜·장소 고르기 → 링크들 → 확정 일시·예약번호·금액·예약한 곳 → 무료 취소 기한·이때까지 예약 → 메모. 예약번호에는 `복사` 단추를 둔다.
- 장소 고르기는 이 여행의 Stop·숙소 장소만 날짜순으로 보이는 간단한 목록이다. 기존 `PlacePickerDialog`는 보관함 전체를 검색하고 숙소를 넣지 않아 쓰지 않는다. 연결된 장소가 일정에서 빠졌으면 편집 시트에 「일정에 없는 장소」로 이름을 보이고 `바꾸기`·`연결 끊기`를 둔다.

```
│ [예약] [정보] [문장]                   │
│ (스페인어 es-ES) (프랑스어 fr-FR)      │

│                          [＋ 문장 더하기] │
```

- `▶` 보통 속도, `🐢` 느리게(rate 0.6) 읽는다. `⋯`에는 `크게 보기`(현지인에게 화면을 보여 줄 때 현지어만 큰 글씨), `복사`, `구글 번역에서 듣기`, `고치기`, `지우기`를 둔다.
- 숙소에 보낼 메시지 같은 긴 글도 문장 하나로 둔다(상황 `lodging`, 500자까지). `크게 보기`와 `복사`로 쓴다.
- 언어 칩은 이 여행의 문장에 들어 있는 `lang`만 보인다.

#### 발음 듣기(`speechSynthesis`)

- `speechSynthesis.getVoices()`에서 고르는 순서: ① `lang`이 정확히 같고 `localService`가 `true`인 음성 ② 앞 두 글자(`es`)가 같은 기기 안 음성 ③ 같은 조건의 원격 음성. 처음에 목록이 비어 있을 수 있어 `voiceschanged`를 최대 2초 기다린다(MDN 예제가 이 이벤트로 목록을 다시 채운다).
- 원격 음성(③)도 쓰되 `▶` 옆에 「온라인 음성」을 작게 적는다. 원격 음성은 브라우저 회사의 서버로 문장을 보내 읽는다. 기기 안 음성만 허용하면 데스크톱 크롬처럼 원격 음성만 있는 환경에서 듣기가 안 되므로 막지 않는다.
- 맞는 음성이 없거나, 2초 안에 목록이 오지 않거나, 재생 중 `error` 이벤트가 오면 `▶` 대신 「이 기기에서 스페인어 음성을 쓸 수 없어요」를 보인다. 그 아래에 `구글 번역에서 듣기` 링크(`translate.google.com`, 문장을 주소에 담아 새 탭)를 둔다. 링크 옆에 「문장이 Google로 전송돼요」를 적는다.
- 개인정보 처리방침의 외부 전송 항목(`src/sections/privacy/privacy-content.ts`)에 「발음 듣기: 원격 음성이나 Google 번역 링크를 쓰면 그 문장이 해당 회사로 전송됨」을 한 줄 더한다(2단계 PR).
- 오프라인: `SpeechSynthesisVoice.localService`가 `true`인 음성은 기기 안 엔진이다. 오프라인에서도 될 가능성이 높지만, MDN은 「오프라인 가능」이라고 쓰지 않는다(§10 확인 필요). 실기기에서 비행기 모드로 확인한다.
- 이 부분은 의존성 없는 작은 모듈(`src/lib/speak.ts`, 약 80줄)로 두고, 음성 고르기 함수만 단위 시험한다.

#### 기본 문장 묶음

- 첫 버전은 **앱에 문장 묶음을 넣지 않는다.** 문장은 사용자가 더하거나 AI가 `library put`으로 채운다. 이유: 앱에 넣는 묶음도 결국 누군가 한 번 써야 하고, 한글 읽는 법의 정확도는 누가 쓰든 같다. 여행 단위로 채우면 그 여행 도시(예: 바르셀로나의 카탈루냐어 인사)에 맞출 수 있다.
- 기본 묶음을 앱에 넣을지는 §7 결정 3으로 남긴다. 넣는다면 언어별 JSON(약 30~40문장, 압축해 언어당 2~3KB)을 `import()`로 지연 로딩한다. `기본 문장 넣기`를 누를 때 해당 언어의 JSON을 받아 여행에 복사한다.

### 5.5 계획 화면·당일 모드와 잇기

- 계획 화면: 그 Stop·숙소의 장소를 `placeId`로 가진 예약을 모두 찾아 줄에 작은 배지를 단다. 한 건이면 `🎫 예약함`·`🎫 예약 전`, 여러 건이면 `🎫 2`처럼 수를 보인다. 누르면 한 건은 편집 시트, 여러 건은 그 장소로 거른 예약 목록을 연다. 같은 숙소가 여러 Day에 있으면 Day마다 같은 배지가 보인다(날짜 없는 예약도 찾을 수 있게 날짜는 맞추지 않는다).
- 당일 모드: `date`가 당일 모드의 「오늘」(04:00 전이면 어제를 오늘로 보는 기존 규칙, `src/domain/trips/today.ts`)과 같은 예약을 맨 위 접힌 카드 `오늘 예약 2`로 보인다. 당일 모드가 보여 주는 일정과 같은 날을 써야 새벽에 두 카드가 어긋나지 않는다. 펼치면 확정 시각·예약번호(복사)·첫 링크가 있다. 공항·매표소에서 바로 꺼내 보기 위해서다.
- 이 둘은 첫 버전 두 번째 PR에 넣는다(§6). 시간이 모자라면 당일 모드 카드를 먼저 넣고 계획 화면 배지는 미룬다. 예약 탭만으로도 찾을 수 있기 때문이다.

## 9. 시험과 확인

- 단위 시험
  - 스키마: 세 필드가 없는 옛 여행 문서를 읽는다. 한도(개수·글자 수)를 넘으면 거부한다. `checkTrip`이 없는 `placeId`·중복 `id`를 잡는다.
  - 동기화(`tests/unit/server/sync-optional-fields.test.ts`): 옛 클라이언트가 `bookings` 없이 올려도 서버 값이 남는다.
  - 두 기기의 예약 목록 동기화(`tests/unit/domain/library-sync/apply.test.ts`). 같은 여행을 동기화한 뒤 A가 먼저, B가 나중에 서로 다른 목록으로 수정한다. 시험마다 같은 초기 상태에서 시작해 기기별 동기화를 순서대로 완료한다.
    - A가 먼저 올리면 B는 받은 A의 목록과 병합해 더 최신인 자기 목록을 올린다. A가 추가 수정 없이 다시 받으면 두 기기 모두 B의 목록을 쓰고, 어느 기기에도 예약 목록 충돌이 생기지 않는다.
    - B가 먼저 올리면 A는 아직 올리지 않은 자기 목록을 B의 목록으로 교체하고, A에만 이전 목록을 충돌로 기록한다.
  - 동기화·묘비 정리(`tests/unit/server/sync-library.test.ts`): 일정에서 빠져 예약만 참조하는 장소가 살아 있거나 묘비여도 여행을 올릴 수 있다. 보존 기간이 지난 장소 묘비도 예약 참조가 남아 있으면 정리하지 않는다.
  - AI 편집(`tests/unit/server/agent-library-edit.test.ts`): 일정에서 빠져 예약만 참조하는 장소의 행이 있으면(묘비 포함) 여행 `put`이 성공하고, 행이 없으면 `invalid-ref`를 반환한다.
  - 중복 장소 정리(`tests/unit/domain/library-sync/repair.test.ts`): 예약만 참조하던 중복 장소를 합치면 그 예약의 `placeId`가 생존 장소 ID로 바뀐다.
  - 크기: 필드 상한을 넘는 문서를 거부한다. 서버 병합 결과가 20만 자를 넘으면 저장하지 않고 `too-large`로 응답한다(`sync-library` 시험 파일).
  - AI `put`(`agent-library-edit` 시험 파일): 준비 필드가 빠진 `put`은 서버 값을 남기고, `[]`를 보내면 지운다. 예약이 없던 여행에 AI가 첫 예약을 넣은 뒤 되돌리면, 응답과 D1 문서 모두 `bookings`가 `[]`이다.
  - 되돌리기: 첫 예약 추가를 되돌리면 `bookings`가 `[]`과 새 시각으로 남는다.
  - 집계: §5.2 표대로 진행률·필수인데 아직·통화별 합계·필터와 「지금 예약할 것」 순서(필수 먼저, 기한순)를 순수 함수로 시험한다.
  - `speak.ts`: 음성 고르기(정확히 일치한 기기 안 음성 → 언어 앞부분 기기 안 음성 → 원격 → 없음).
  - 함께 편집 적용이 준비 필드를 지우지 않는다(§4.4, `apply.ts`의 기존 시험 파일에 사례 하나).
  - 공유에서 빠짐: 가짜 예약번호를 넣은 여행으로 일정 공유(`build-trip-share.ts`)·갱신 링크(`build-live-doc.ts`)·함께 편집 문서(`trip-collab/build-doc.ts`)를 만들고, 직렬화 결과에 세 필드 이름과 예약번호가 없는지 본다.
- 화면 시험: 예약 하나 더하기 → 상태 바꾸기 → 집계 숫자가 바뀜. 컴포넌트 시험 하나로 한다(Playwright는 더하지 않음).
- 실기기 확인(사람). iPhone Safari·안드로이드 크롬에서 온라인일 때 es-ES·fr-FR 문장 `▶`와 음성이 없을 때의 안내를 확인하고, 비행기 모드에서는 다음을 각각 확인한다.
  1. 앱 신규 실행. 앱을 닫고 비행기 모드에서 다시 열었을 때의 결과를 기록한다.
  2. 준비 화면 최초 진입. 온라인에서 여행 계획 화면을 연 뒤, 준비 화면을 처음 열기 전에 비행기 모드로 바꾼다. `준비`를 눌러 결과를 기록한다.
  3. 이미 열린 준비 화면. 온라인에서 준비 화면을 열어 둔 뒤 비행기 모드로 바꿔 저장된 정보가 보이는지와 문장 탭에서 es-ES·fr-FR 발음이 재생되는지를 각각 확인한다(§5.4).
- 준비 화면을 넣는 PR에서 `package.json`의 `build:ci`에 있는 `yarn size` 호출에 `--require-lazy <준비 화면 청크 이름>`을 추가한다. 이 옵션으로 준비 화면 청크가 따로 생성되고 첫 로딩 목록에서 빠져 있는지 확인한다. 각 PR을 끝내기 전에 `yarn build:ci`를 실행해 첫 로딩 JS gzip 예산을 확인한다.
- **구현 계획 때 반영할 검토 지적(2회차 Warning·Suggestion, 기획 단계에서는 고치지 않음).** 구현 계획서를 쓸 때 하나씩 판단한다.
  - 금액은 `Schema.Finite`로 유한한 0 이상의 수만 받는다(`1e309` 같은 입력이 `Infinity`로 통과해 저장 뒤 `null`이 되는 문제).
  - 당일 모드에서 다른 Day를 골랐을 때 `오늘 예약`이 실제 오늘을 따를지 고른 Day를 따를지 정한다(추천: 고른 Day를 따르고 카드 제목에 날짜를 적는다).
  - 롤백 절차 2단계에 앱의 `AI 변경 기록 › 되돌리기`도 쓰지 않는다고 적는다(이 경로는 `LIBRARY_SYNC=off`·`AGENT_EDIT=off`로 막히지 않는다).
  - 일정 편집이나 수신 병합으로 여행이 20만 자를 넘는 경우의 안내(지금도 동기화의 「올리지 못한 항목」으로 보인다).
  - AI 되돌리기가 이미 정리된 장소 묘비를 다시 가리키는 경우(예약만 참조하던 장소가 90일 뒤 정리된 다음 되돌림).
  - 처리방침·AI 연결 안내에 예약번호가 `library:read` 토큰·AI 변경 기록(30일)·서버 백업에도 남는다는 점을 적는다.
  - 일정 공유 v2·v3 모두에서 준비 필드가 빠지는지 시험한다.
- **실제로 쓰는지 확인할 시점: 2027-01-10.** 이베리아 여행에서 예약 탭·문장 탭을 열어 봤는지 사용자에게 묻는다. 쓰지 않은 탭은 걷어내는 PR을 제안한다.

확인 날짜는 모두 2026-11-27이다.

**확인 필요**

- iOS Safari에서 `speak()`에 사용자 동작(탭)이 필요한지. 버튼을 눌러 읽으므로 영향은 작다고 본다.
- 안드로이드 크롬의 `speechSynthesis`가 시스템 TTS 엔진을 쓰는지, 음성 데이터를 받아 두면 오프라인에서 되는지. 공식 문서에서 찾지 못했다. 실기기로 확인한다.
- iOS에서 사용자가 추가 음성을 받는 설정 경로. 안내 문구를 쓰기 전에 실기기로 확인한다.
- 카탈루냐어(ca-ES) 음성이 iOS·안드로이드에 있는지. 바르셀로나에서도 스페인어가 통하므로 첫 버전은 스페인어만 가정한다.
- Open-Meteo 요금 안내의 FAQ에는 「과거·기후 API는 Professional 이상」이라는 문장이 있고, 요금 표에는 무료로 되어 있어 서로 다르다. 결정 1에서 「다」를 고를 때만 다시 확인한다.
- 구글 번역 링크의 주소 형식(`?sl=auto&tl=es&text=…&op=translate`)은 공식 문서가 없다. 구현 때 실제로 열어 확인한다.
