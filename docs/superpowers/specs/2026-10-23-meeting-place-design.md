# 약속장소 정하기 설계

여러 사람의 출발지에서 공평한 모일 곳을 찾고, 후보를 링크로 보내 함께 고른 뒤 확정한다.
계정·서버 DB가 없으므로 사람 사이의 상태는 모두 링크(후보·답장·확정)로 주고받고, 집계는 주최자 기기에서만 한다.

## 결정 요약(브레인스토밍 2026-10-23)

| 항목 | 결정 |
|---|---|
| 목적 | 중간 지점 찾기 + 후보를 공유해 함께 고르기 |
| 소요시간 기준 | 약속마다 대중교통 / 자동차 / 직선거리 중 고른다 |
| 출발지 입력 | 이름 검색(네이버 자동완성), 지도 핀, 내 보관함 장소 |
| 후보 | 번화가 역(전국 주요 역 약 150곳, 앱에 내장) + 그 근처의 내 보관함 장소 |
| 순위 | 기본 '가장 먼 사람'(최장 시간 → 같으면 평균). 화면에서 평균·편차로 바꿔 비교 |
| 함께 고르기 | 답장 링크 모으기. 친구는 좋아요 여러 개, 자기 출발지 수정 가능 |
| 출발지 수집 | 주최자가 넣고, 친구가 답장에서 고칠 수 있다 |
| 일시 | 넣을 수 있고 대중교통 조회에 반영 |
| 확정 뒤 | 확정 링크(장소·일시·참석자별 길찾기) |
| 보관 | 약속 목록으로 보관, 보관함에 넣어 백업에 포함 |
| 위치 | 새 탭 '약속' |
| 친구 화면 | 본 앱의 `/meet` 경로(지연 로딩). 따로 만든 가벼운 페이지는 쓰지 않는다 |

## 사용 흐름

### 주최자('약속' 탭)

1. 약속 목록 → '새 약속'. 제목(필수), 일시(선택, 날짜+시각), 이동수단(대중교통 기본)을 정한다.
2. 참석자를 넣는다. 이름(필수)과 출발지(검색·지도 핀·보관함 장소). 처음 한 명은 '나'로 미리 만든다.
   출발지가 없는 참석자는 계산에서 빠지고 "출발지 없음"으로 표시한다. 출발지가 있는 참석자가 2명 이상이어야 계산한다.
3. '중간 지점 찾기' → 번화가 역 순위(최대 8곳). 각 역에 참석자별 소요시간과 최장·평균·편차가 보이고,
   순위 기준 단추(가장 먼 사람 / 평균 / 편차)로 다시 정렬한다. 기준은 약속에 저장한다.
4. 역을 누르면 그 역 반경 1km 안의 내 보관함 장소가 나온다(라벨로 거르기). 역 자체나 장소를 후보에 담는다.
   후보는 최대 8곳이며, 장소 후보도 참석자별 소요시간을 조회해 같은 표에 보인다.
5. '후보 링크 보내기' → Web Share API(없으면 클립보드 복사). 주최자의 좋아요는 화면에서 바로 누른다.
6. 친구의 답장 링크를 열면 미리보기("○○님 답장: 좋아요 2곳, 출발지 바뀜")가 뜨고 '반영'하면 집계에 더한다.
   출발지가 바뀌면 그 참석자의 소요시간을 다시 조회한다.
7. 집계표(후보별 좋아요 수·누가 좋아했는지·소요시간)에서 후보를 '확정' → '확정 링크 보내기'.
   확정은 취소할 수 있다(다시 고르기).

### 친구(`/meet#d=…`)

1. 약속 제목·일시·이동수단과 후보 지도·목록이 보인다.
2. "나는 누구?" — 참석자 목록에서 고르거나 '목록에 없어요'로 새 이름을 넣는다.
3. 내 출발지를 확인한다. 고치려면 검색·지도 핀·자기 보관함 장소를 쓴다. 고치면 이 기기에서 내 소요시간만 다시 조회한다.
4. 후보마다 참석자별 소요시간(주최자가 계산해 링크에 넣은 값, 내 출발지를 고쳤으면 내 줄은 새 값)이 보인다.
   좋아요를 여러 개 누른다(0개도 답장할 수 있다).
5. '답장 링크 보내기' → Web Share API 또는 클립보드. 친구 기기의 보관함은 바꾸지 않는다.
   이 기기의 답장 초안(누구·출발지·좋아요)은 localStorage `tripmap:meet-drafts:v1`에 약속 id별로 최대 20개 둔다(편의용, 실패해도 동작).

### 확정(`/meet#f=…`)

제목·일시·장소 지도와 주소, 참석자별 "○○ 출발 길찾기" 단추(네이버 지도, 약속의 이동수단; 직선거리 약속은 대중교통).

### 링크를 연 기기에 따른 처리(`/meet`)

| 해시 | 처리 |
|---|---|
| `#d=` | 친구 화면. 이 기기에 같은 id의 약속이 있으면(주최자 본인) '내 약속 열기' 단추를 함께 보인다 |
| `#r=` | 같은 id의 약속이 있으면 답장 미리보기 → '반영' 뒤 `/meetings/<id>`로. 없으면 "이 기기에 없는 약속의 답장이에요" 안내만 하고 아무것도 바꾸지 않는다 |
| `#f=` | 확정 화면. 누구나 볼 수 있다 |
| 깨짐·없음 | "링크를 읽지 못했어요" 안내와 약속 목록으로 가는 단추 |

해시는 읽은 뒤 `history.replaceState`로 지우지 않는다(새로고침해도 같은 화면). 앱 바깥으로 보내지 않는다.

## 저장 형식

보관함 `LibrarySchema`에 선택 키 `meetings: Record<MeetingId, Meeting>`를 더한다. schemaVersion은 2 그대로다.
키는 기존처럼 일반 `String`이고 key===id를 검사한다. 칸은 기존 `FieldSchema`(값+updatedAt, 필드 단위 LWW)를 쓴다.

```
Meeting = {
  id: PlaceId와 같은 10자 형식,
  title: Field<string 1~60자>,
  at: Field<{ date: CalendarDate, time: HHmm } | null>,
  mode: Field<'transit' | 'car' | 'straight'>,
  rank: Field<'max' | 'avg' | 'spread'>,
  participants: Field<Participant[]>,   // 최대 10
  candidates: Field<Candidate[]>,       // 최대 8
  replies: Field<Record<ParticipantId, { likes: CandidateId[], sentAt: ISO, receivedAt: ISO }>>,  // 주최자 본인은 sentAt=receivedAt
  decided: Field<CandidateId | null>,
  createdAt: ISO, deletedAt: ISO | null,
}
Participant = { id: 8자, name: 1~20자, origin: Origin | null }
Origin = { name: 1~60자, lng, lat, placeId?: PlaceId }        // 좌표는 한국 범위(경도 124~132, 위도 33~39)
Candidate = { id: 8자, kind: 'hub' | 'place', name: 1~60자, address?: ≤120자, lng, lat, hubId?: string, placeId?: PlaceId }
```

- 검사: 참석자·후보 id 중복 없음, `replies` 키와 `likes`·`decided`가 살아 있는 참석자·후보를 가리킴(아니면 무효).
  후보·참석자를 지우면 그를 가리키는 좋아요·답장·확정을 같은 갱신에서 함께 지운다.
- 약속은 최대 200개(삭제 표시 포함). 지우면 `deletedAt`만 남기고(여행과 같은 관례) 목록에서 숨긴다.
- 주최자 본인의 좋아요도 `replies[나의 참석자 id]`에 넣는다.
- 소요시간은 저장하지 않는다. 경로 조회 캐시(`tripmap:routes:v1`)가 맡는다.
- `placeId`는 참고용이다. 장소가 지워져도 이름·좌표로 계속 쓰며 dangling 검사를 하지 않는다.

### 옛 버전 호환

- 새 버전은 `meetings`가 없는 옛 문서를 그대로 읽는다.
- **v0.14.8 이하는 모르는 `meetings`를 떼어 낸다.** 그 버전에서 보관함에 무엇이든 저장하면 약속이 모두 사라진다.
  백업 파일은 원본 JSON을 담으므로 약속도 들어간다. 롤백 전에 전체 백업을 받고, 새 버전으로 돌아온 뒤 복원한다.
  이 내용을 `docs/rollback.md`의 v0.15.0 행 "되돌릴 때 영향"에 적는다(v0.14.7 라벨 이모지 선례).
- 공유 파일·공유 링크(`/view`, `/import`) 형식은 바꾸지 않는다. 약속은 그쪽으로 내보내지 않는다.

## 링크 형식

기존 공유 링크와 같은 인코딩(JSON → `deflate-raw` → base64url)으로 `/meet#<kind>=<data>`에 싣는다.
문서마다 `format: 'tripmap-meet'`, `v: 1`, `kind`를 두고 `onExcessProperty: 'error'`로 엄격히 검증한다.
해시는 최대 8,000자, 풀었을 때 64KB 이하. 링크의 이름·주소는 저장 형식과 같은 길이 제한, 좌표는 한국 범위.

| kind | 내용 |
|---|---|
| `d` 후보 | `meetingId`, `title`, `at`, `mode`, `participants[{id,name,origin}]`, `candidates[{id,kind,name,address?,lng,lat}]`, `times`: 후보 id → 참석자 id → 분(정수) 또는 null(경로 없음·미계산), `sentAt` |
| `r` 답장 | `meetingId`, `participantId`(목록에서 골랐을 때) 또는 `newName`, `origin`(바꿨을 때만), `likes[]`, `sentAt` |
| `f` 확정 | `title`, `at`, `mode`, `place{name,address?,lng,lat}`, `participants[{name,origin}]` |

- 직선거리 약속의 `times`는 분이 아니라 미터를 담고 화면은 km로 그린다(`unit: 'm' | 'min'`).
- 답장 반영 규칙
  - `participantId`가 살아 있으면 그 참석자의 답장을 새것으로 덮는다(같은 사람의 두 번째 답장). 링크의 `sentAt`이 저장된 답장의 `sentAt`보다 오래되면 "더 오래된 답장이에요"를 보이고 반영하지 않는다.
  - `newName`이면 같은 이름(공백 정리·NFC 비교)의 참석자가 있으면 그 사람으로, 없으면 새 참석자로 더한다. 10명이 차 있으면 반영하지 않고 안내한다.
  - `origin`이 있으면 그 참석자의 출발지를 바꾼다.
  - 지금 약속에 없는 후보 id의 좋아요는 버리고 미리보기에 "없어진 후보 n곳 제외"로 보인다.
  - 확정된 약속에도 반영은 되지만 확정은 그대로 둔다.

## 계산

### 번화가 역 데이터

- 전국 주요 역·번화가 약 150곳(수도권 약 80, 광역시·도청 소재지·KTX 주요 역·강원 중심지 약 70)을
  `src/domain/meeting/hubs-data.ts`에 `{ id, name, region, lng, lat }`로 둔다. 지연 로딩 덩어리에만 들어간다.
- 좌표는 `scripts/build-hubs.mjs`가 이름 목록(`scripts/hubs-list.json`, 150곳)을 `/api/search`와 같은 네이버 자동완성으로 조회해
  역·터미널·공항 분류(출구·주차장·방면 제외)의 첫 결과로 만든다. 2026-10-24에 만들어 결과를 확인하고 커밋했다. 앱 실행 중에는 이 스크립트를 쓰지 않는다.

### 중간 지점 찾기

1. 출발지가 있는 참석자들에서 각 역까지 직선거리(하버사인)를 구해, '가장 먼 사람 직선거리'가 짧은 순으로 역 8곳을 고른다.
2. 이동수단이 직선거리면 그 값으로 끝낸다.
3. 대중교통·자동차면 참석자 × 8곳 경로를 조회한다(동시 4개, 기존 `RouteLookup` 제한). 진행률("12/32")을 보인다.
   경로가 없는 칸은 null이고, null이 있는 역은 순위에서 아래로 보내되 목록에는 남긴다.
4. 순위 기준
   - 가장 먼 사람(`max`): 최장값 오름차순, 같으면 평균 오름차순.
   - 평균(`avg`): 평균 오름차순, 같으면 최장값.
   - 편차(`spread`): 최장값−최단값 오름차순, 같으면 최장값.
5. 출발지·이동수단·일시가 바뀌면 결과에 "조건이 바뀌었어요 — 다시 찾기"를 보인다(자동 재조회 안 함).

### 대중교통 출발 시각

일시가 있으면 `약속 시각 − 60분`을 출발 시각으로 조회하고, 없으면 지금 시각으로 조회한다.
화면에 "대중교통: 10/31 17:00 출발 기준, 조회 2026-10-23" / "자동차: 조회 시점 실시간 교통 기준"을 적는다.

## 서버

### 대중교통 경로: `/api/route` 확장

- `mode=transit&from=경도,위도&to=경도,위도&at=YYYY-MM-DDTHH:mm`(한국 시각, transit에는 필수 — 클라이언트가 일시 또는 지금 시각으로 채운다).
- 네이버 `https://map.naver.com/p/api/directions/pubtrans?start=…&goal=…&crs=EPSG:4326&mode=TIME&lang=ko&departureTime=…`를 기존과 같은 헤더(브라우저 UA, Referer)로 부른다.
  응답이 400~700KB라서 첫 경로(`paths[0]`, 추천순)의 요약만 돌려준다:
  `{ mode:'transit', distanceM, durationS, fare|null, transfers, walkS, path: [], queriedAt }`.
  `status`가 `POINTS_ARE_TOO_CLOSE`(약 100m 안, 2026-10-24 확인)면 같은 두 점의 도보 경로를 불러 그 시간·거리를 `transfers: 0, fare: 0`으로 돌려준다.
  그 밖에 `paths`가 비면 `NO_ROUTE`. 출발·도착이 10m 안이면 기존 클라이언트 처리대로 서버를 부르지 않고 0으로 본다.
  네이버의 `duration`·`walkingDuration`은 분 단위라 초로 바꾼다.
- 캐시 키에 `at`을 10분 단위로 내린 값을 넣고 max-age 1시간. 입력 키 형식 `transit:<at>:lng,lat>lng,lat`.
- 여행 계획의 구간 수단(`car|walk`)과 여행 저장 형식은 바꾸지 않는다.
- 위험: 큰 응답의 `JSON.parse`가 Cloudflare 함수 CPU 한도에 걸릴 수 있다. 미리보기 배포에서 서울 시내·장거리 두 경우를 실제로 불러 확인한다.

### 이름 검색: `/api/search` 신설

- `q`(1~40자), `near=경도,위도`(선택) → 네이버 `https://map.naver.com/p/api/search/instant-search?query=…&coords=위도,경도`.
- `place[]`만 최대 10개 `{ name, address(도로명 우선), category, lng, lat }`로 돌려준다. 좌표가 한국 범위 밖이면 버린다.
- 캐시 7일. 허용 출처·에러 형식은 기존 `handleGet`·`http.ts` 그대로.
- 위험: 공식 API가 아니다. 막히면 `UPSTREAM_ERROR`로 "검색이 안 돼요 — 지도 핀이나 보관함 장소를 써 주세요"를 보인다.
  `allSearch`는 캡차를 요구해 쓰지 않는다(2026-10-23 확인).

### 클라이언트 경로 조회

`RouteLookup.leg`가 `transit`과 출발 시각을 받는다. 로컬 캐시 키에도 `at`(10분 단위)을 넣는다.
기존 여행 계획 호출은 그대로 동작해야 한다.

## 길찾기 연결

`naverDirectionsUrl`의 `mode`에 `'transit'`을 더한다. 앱은 `nmap://route/public?…`, 웹은 `…/-/transit`.
웹 주소의 수단 이름 `transit`은 map.naver.com 웹 번들(`pcweb_navermap_v5/261014-5059ff3/index-5059ff3.js`)의
길찾기 수단 상수 `{CAR:"car",TRANSIT:"transit",WALK:"walk",BIKE:"bike"}`로 확인했다(2026-10-24).

## 화면

- 경로: `/meetings`(목록), `/meetings/:id`(약속 편집), `/meet`(링크 화면). 모두 `lazy-routes.ts`의 `lazyChunk`+`lazy`로 지연 로딩하고
  `ROUTE_CHUNKS`에 넣어 한가할 때 미리 받는다. 첫 로딩 JS에 들어가지 않는다(`build:ci --require-lazy`에 `MeetingsPage`, `MeetingEditorPage`, `MeetLinkPage`).
- 탭: `NAV_ITEMS`에 '약속'을 '여행' 다음에 더한다(아래 탭 6개, 360px에서 칸마다 44px 이상).
- 약속 목록: 카드(제목·일시·참석자 수·후보 수·확정 장소). 빈 상태 안내.
- 약속 편집(한 화면, 넓은 화면은 왼쪽 패널+오른쪽 지도, 좁은 화면은 위 지도+아래 시트)
  - 기본 정보(제목·일시·이동수단)
  - 참석자 목록(이름·출발지·답장 받음 표시, 출발지 고르기: 검색 상자 / 지도에서 고르기 / 보관함에서)
  - 중간 지점 결과(역 순위, 기준 단추, 역별 근처 보관함 장소)
  - 후보와 집계(좋아요 수·누가·소요시간 표, 확정)
  - 단추: 후보 링크 보내기, 확정 링크 보내기
- 지도: 출발지(참석자 이름 머리글자 점), 역 순위(번호), 후보(강조), 확정 장소. 기존 `MapView`·`MapMarker`를 쓴다.
- 지도에서 고르기: 기존 핀 모드와 같은 가운데 십자선 방식이지만 `addFlowAtom`에 묶지 않은 별도 오버레이로 만든다(장소 추가 흐름은 건드리지 않는다).
- 라벨을 그릴 때는 이름(과 이모지)만 쓰고 선 아이콘은 쓰지 않는다(라벨 아이콘 제거 작업과 맞춤).
- 사용자 문자열은 React 텍스트로만 그린다. `dangerouslySetInnerHTML` 금지. 문구는 한국어.
- 오프라인: 목록·편집·링크 화면은 열리고, 경로·검색 조회만 "오프라인이에요"로 막는다.

## 오류 처리

- 경로 조회 실패 칸은 "—"와 다시 시도 단추. 시간 초과·오프라인·네이버 오류를 기존 `RouteLookupError` 코드대로 문구를 나눈다.
- 링크 해석 실패는 화면 전체 안내 한 가지("링크를 읽지 못했어요")로 보이고 원인 코드는 콘솔에만.
- 저장 실패(용량 초과 등)는 기존 보관함 저장 오류 알림을 쓴다.

## 시험

- 단위: 약속 스키마(정상·제한·dangling), 답장 반영 규칙 표 전체, 순위 3기준과 null 처리, 직선 사전 선별, 링크 인코딩 왕복·엄격 검증·크기 제한,
  `/api/route` transit·`/api/search` 해석(잘라 낸 작은 응답 고정물, 700KB 원본은 커밋하지 않음), 함수 진입점(출처·캐시), `RouteLookup` transit 캐시 키,
  `naverDirectionsUrl` transit, 옛 문서(meetings 없음) 읽기.
- E2E(`tests/e2e/meetings.spec.ts`, desktop·iphone·galaxy `testMatch`에 추가, 한 시나리오는 `@smoke`):
  가짜 지도·`/api/route`·`/api/search` 가로채기로 약속 만들기 → 참석자 3명 → 중간 지점 찾기 → 후보 담기 → 후보 링크 →
  새 브라우저 맥락에서 친구로 열어 출발지 수정·좋아요 → 답장 링크 → 주최자 맥락에서 반영 → 확정 → 확정 링크 화면.
  답장을 모르는 기기에서 연 경우, 깨진 링크.
- 첫 로딩 예산 `initialJsGzipMax` 327,680 이하 유지, `--require-lazy` 통과.
